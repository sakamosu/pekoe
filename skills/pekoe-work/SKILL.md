# pekoe の作業セッションで任された作業を進める

自分は依頼元(tapi・main のエージェント・人)から 1 つの作業を任されたセッション。この worktree で直接作業し、終わったら結果と証拠を `pekoe report` で依頼元に返す。依頼元は報告を `pekoe wait` で待っているので、報告しないと終わったことが伝わらない。

- 自分がセッションの側かは pekoe スキルの判定(`git rev-parse --path-format=absolute --git-dir --git-common-dir` の 2 行が違う = linked worktree)で確かめる
- この worktree で直接編集する。`pekoe new` で孫セッションを作らない(並行させたい明確な理由があるときを除く)
- プロンプトの完了条件・やらないことを最優先にする。下の手順と食い違えば(「push しない」「land しない」など)プロンプトに従う

## 流れ

1. **計画**: プロンプトを読み、関係するコードを調べ、何をどう変えるかを決める。完了条件が曖昧なら、自分で妥当な線を決めて報告に書く(依頼元に聞くのは、決めようがないときだけ。下の「詰まったら」)
2. **実装**: リポジトリの CLAUDE.md・既存の書き方に合わせる。範囲外の変更をしない
3. **テスト**: リポジトリのテストを実際に動かす。新しい振る舞いにはテストを足す
4. **確かめる**: 下の「確かめ方」。テストが通っただけで終わりにしない
5. **独立レビュー**: 下の「独立レビュー」
6. **コミット**: 論理単位で分ける。メッセージはリポジトリの慣習に合わせる
7. **land**: `pekoe land <slug>`(slug は `$PEKOE_SESSION`)。rebase → テスト → push → PR 作成を pekoed がやる。失敗したら理由を読んで直し、もう一度。マージは人がする
8. **報告**: `pekoe report`(下)

## 確かめ方

- 「CI が通った」「テストが通った」だけでは確かめたことにならない。変えた振る舞いを実際に動かして見る
  - UI: 画面のスクショか GIF を撮り、パスを evidence に付ける。自分の sandbox ではポートを開けないので、dev server は `pekoe dev <自分の slug>`(`$PEKOE_SESSION`)で pekoed に起動してもらう(リポジトリの設定の `[hooks] dev` が、セッションのポートで pekoe の sandbox の中で動く。ポートは `pekoe --json ls` の `port`、動いているかは `dev`)。受信箱で人に頼まない。同じコマンドは起動と停止を切り替える(動いている間に打つと止まる)ので、確かめ終わったら止める。効くのは自分のセッションだけで、別の slug は断られる。`[hooks] dev` が無い・つなげない(sandbox が localhost への接続を断る)ときは、そう報告に書く
  - API・CLI: 実際のリクエストとレスポンス(コマンドと出力)をファイルに残し、evidence に付ける
  - バグ修正: 直す前に再現し、直した後に再現しないことを見る
- 何も実行せずに「直した」「動く」と言わない。動かせなかったもの(環境が無い、sandbox で塞がれた)は、そう報告に書く
- 失敗したテストを消す・飛ばす・期待値を実装に合わせて書き換えるのは、それが正しいと説明できるときだけ。説明を報告に書く

## 独立レビュー

自分の差分を自分の文脈で読み直すだけではレビューにならない。作者でないエージェントに読ませる:

- 頼む前に、レビューを始めた印を残す: `pekoe report "独立レビューを頼んだ" --status review --verdict pending --reviewed-sha <sha>`。ダッシュボードの工程表はこれで review を「進行中」にする(印がないと、待っている間も impl のまま・ターンを終えると done に見える)。pending は合格ではない(マージの根拠にならない)
- サブエージェント(Agent ツール)を立て、pekoe-review スキルに従ってレビューさせる。渡すのは、この作業の目的と完了条件、base のブランチ、レビューする HEAD の SHA(`git rev-parse HEAD`)。自分の結論(「ここは大丈夫」など)は渡さない
- 不合格なら指摘を直し、コミットし直して、新しい SHA で印を残し直してから、もう一度レビューさせる
- 合否はレビュアーが `pekoe report --status review --verdict pass|fail --reviewed-sha <sha>` で残す(サブエージェントはこのセッションの窓の中で動くので、報告はこのセッションに付く)。land するのは合格の後。land の rebase で SHA が変わっても、差分の中身が同じなら pekoed が合格を引き継ぐ(中身が変わったら再レビュー)
- プロンプトに「独立レビューは別のセッションでやる」とあれば、サブエージェントは立てずに land まで進め、報告にそう書く

## 報告(pekoe report)

```sh
pekoe report "<1〜3 行の要約>" --status done \
  --evidence <PR の URL> --evidence <スクショやログのパス>
pekoe report - --status done < report.md     # 長文は stdin
```

- `--status`: `done`(終わった)・`blocked`(詰まった)・`progress`(途中経過。長い作業の節目に)。`--evidence` は何度でも付けられる(20 件まで、要約は 4000 文字まで)
- どのセッションの報告かは pekoed が呼び出したプロセスから決める。slug を渡す引数は無い(自分のセッションの分しか書けない)
- pekoed は証拠のファイルを読まない(パスと URL を文字列として残すだけ)。人が開けるパスにする
- 報告しても `state` は変わらない。報告した後に止まると、依頼元の `pekoe wait` には `report` と `done` の両方が届く
- 要約に書くもの: 何を変えたか、どう確かめたか(実行したコマンド)、独立レビューの結果、残っていること・やらなかったこと
- evidence には PR の URL と、確かめた証拠(スクショ・GIF・ログのファイル)を付ける。パスは worktree の中か一時ディレクトリの絶対パス
- 報告したら止まってよい。依頼元から追加の指示が来たら(`pekoe send` で入力欄に届く)続ける

## 詰まったら

- 自分で決められること(実装の方針、どちらの書き方にするか)は決めて進め、報告に書く
- 依頼元の判断が要る(完了条件が矛盾している、範囲を広げないと直らない): `pekoe report - --status blocked` に、何が分かっていて何を決めてほしいかを書いて止まる
- 人にしかできないこと(ログイン、認証情報、外部サービスの設定、許可の変更)だけは `pekoe --json ask-human "<頼むこと>" --kind login`(問いは自分のセッションに付き、pekoed がブランチ・差分などの事実を添える)。答え(「済んだ」「できない」)は `pekoe --json ask-human --wait <id>` で待つか、止まっていれば入力欄に `[pekoe inbox #<id>] 答え: …` の 1 行で届く。要らなくなったら `pekoe --json inbox withdraw <id>`
- sandbox で断られた(書き込み・ネットワーク)ら回避しない。何が断られたかを `--status blocked` で報告する

## やらないこと

- マージ、`pekoe rm`、他のセッションへの `pekoe send`、`pekoe answer`
- 依頼元や人に頼まれていない範囲の変更、ついでのリファクタリング
- 報告せずに止まる(終わったときも詰まったときも `pekoe report`)
