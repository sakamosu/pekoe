# プロジェクトの層 — 設計書(未決事項 U11)

状態: 設計中(コードなし)。[orchestration.md](orchestration.md) の段階 4 に残っている「プロジェクト担当の層とプロジェクトのボード」(未決事項 U11)を、作るかどうか・どこまで作るかを決めるための文書。決めるのは利用者で、この文書は材料と推奨を出す。決まったら、決めたことと理由を orchestration.md の U11 に戻し、仕様は実装と一緒に [api.md](api.md) に書く。

## 何を決めるか

今の層は **人 → tapi → セッション** の 2 段で、tapi が人の依頼を記録し(依頼(ledger))、セッションに `--request` で結び、ダッシュボードの工程表は依頼元と依頼でセッションをまとめる。この上に「プロジェクト」(いくつかの依頼・PR のまとまり)を足すなら何を作るか、を決める。

- U11 の今の推奨は「(a) 作らない。複数 PR のまとまりが日常的になってから、記録した依頼を『プログラム』に育てる形で考える」
- この文書は、実際の使われ方を数えて「日常的になったか」「足りないのは何か」を見て、案を 3 つ並べる

## 前提

今あるもの(仕様は [api.md](api.md) の「依頼(ledger)」「Session オブジェクト」「集計(stats)」、理由は [orchestration.md](orchestration.md)):

- 依頼(ledger): tapi への人の入力を記録し、tapi が `done` / `drop` / `chat` で閉じる。雑談は pekoed が自動で閉じる(U16)。セッションは `--request` / `ledger link` で結ぶ。main をハブにするときは使わない(U13)
- `Session.parent`(依頼元)・`Session.request`(依頼)・`Session.after`(順序。今は記録と表示だけで、起動は止めない)
- ダッシュボード(TUI の [4]・Web UI)の工程表: 依頼元と依頼でまとめ、セッションごとに `impl → review → PR → CI → merge`
- `pekoe stats`: 日付・リポジトリごとのマージ数とトークン

並行して進んでいて、**まだマージされていない**もの(この文書は入った後の姿を前提にする。中身が変われば、下の「前提が変わったら」を見直す):

- **tapi への配送**(orchestration.md の「3. tapi への配送」): `pekoe wait` を使わないエージェントにも、たまった変化を 1 通にまとめて tapi に届ける
- **負荷の制御**(段階 4 の G の残り): 同時に動かすセッションの上限と、`--after` の待ち合わせ(先のセッションが済むまで後のセッションを起動しない)。ここでは「作ったセッションが、上限か `--after` で待ち行列に入れる」ようになると仮定する

| 今あるセッションの `parent` | `+tapi` が 6 本、別のリポジトリの main セッションが 1 本(main をハブにする使い方も続いている) |

読み取れること:

1. **依頼の大半は 1 本・1 時間以内で閉じる。** 複数 PR が何日も続く「プロジェクト」は、まだ日常ではない。2 本以上の依頼 16 件も、ほとんどが 1〜2 日で済み、今の工程表の「依頼でまとめる」で一覧できている
2. **足りないのは「まだセッションになっていない項目」の置き場所。** tapi は案を番号つきで出し、人は短い返事で番号を選ぶ(16 件。全部のこともあれば一部のこともある)。一部だけ選んで残りを後に回すこともある(4 件)。番号の中身・後に回した項目は tapi の会話にしかなく、依頼の記録・ダッシュボードには出ない。`tapi reset` すると消え、人が「残りはどうなった?」を確かめる道もない。後に回した 4 件のうち、進行中の #696 を除く 3 件の残りがその後どうなったかは、記録からは辿れなかった
3. **一番大きな例が、この文書を頼んだ依頼(#696)。** 「1 と 2 を仕上げて、その後 4・5・6」の 5 本で、今までで最多。1・2 がマージされた後の「4・5・6 進めて」は別の依頼(#697)として記録され、#696 とはつながっていない。「4・5・6」が何を指すかは tapi の会話と orchestration.md の段階の一覧にしかない
4. **「続き」の依頼(15 件)は今の仕組みで困っていない。** 同じセッションに `ledger link` で結べば、工程表で同じ行に出る
5. **順序(`--after`)は使われていない。** #696 の 5 本も順序があるのに `after` は空で、tapi は先のものがマージされてから後のものを作っている。負荷の制御で `--after` が待つようになれば、先に作っておく使い方ができる

まとめると、今ほしいのは「プロジェクトの担当者」ではなく、**依頼の中の段取り(まだ始めていない項目を含む)を、tapi の会話の外に残して見せる道**。

## 案

### 案 A: 作らない(今のまま)

U11 の今の推奨。コードは変えず、tapi のスキル(`skills/pekoe-orchestrate/SKILL.md`)に書き足すだけにする。

- **データの形**: 変えない。番号つきの案と後に回した項目は、tapi が依頼の `note` か報告の要約に書く(`ledger done` の `--note` は閉じるときにしか書けないので、続きのある依頼では書けない)
- **CLI**: 変えない
- **ボード**: 変えない。工程表は今どおりセッションがあるものだけ
- **tapi の手順**: 「一部だけ選ばれたら、残りを人への返事の最後に毎回書き直す」「リセットの後は orchestration.md や PR を読み直して思い出す」をスキルに足す
- **コスト**: ほぼゼロ
- **危険**: 困りごとの 2・3 が残る。後に回した項目は tapi の会話が流れれば消え、人もダッシュボードで気づけない。tapi が覚え直すために読むもの(文書・PR)が増え、トークンも増える

### 案 B: 依頼に段取りを持たせる(軽い形)

依頼(ledger)に「段取り」(番号つきの項目の並び)を足す。項目はセッションに結べ、まだ結んでいない項目は `todo` として工程表に出る。プロジェクトという新しいものは作らず、依頼そのものを「プログラム」に育てる(U11 の推奨の延長)。

- **データの形**: state.db に `ledger_steps(request, n, text, status, slug, note, at, closed_at)`(主キーは `request, n`)。`LedgerEntry` に `steps: [{n, text, status, slug?, note?}]` を足す
  - `status` に持つのは `todo`・`dropped`・`done`(人が自分でやった、などセッションのない項目を閉じる)と、結んだ `slug` だけ。結んだ項目の進み具合はセッションから計算する(工程表と同じ。landed か PR がマージ済みなら済み)
  - 上限: 1 つの依頼に 20 項目、1 項目 200 文字。文は tapi(エージェント)が書くので、受信箱と同じく制御文字を落とし、表示ではエージェントの文として扱う
  - 書けるのは tapi と人(依頼(ledger)と同じ。main からは断る: U13)
- **CLI**(案):
  - `pekoe ledger plan <id> "<項目>"...` 項目を後ろに足す(番号は 1 から続き番号)
  - `pekoe new … --request <id> --step <n>` 作ったセッションをその項目に結ぶ(`--request` だけなら今どおり)。後からなら `pekoe ledger link <id> <slug> --step <n>`
  - `pekoe ledger step <id> <n> --done [--note …]` / `--drop --note …`(理由は必須) / `--todo`(結び直し・戻し)
  - `pekoe ledger <id>` と `pekoe --json ledger` に段取りを出す(`3/6 done · 2 todo` と、項目ごとの状態)
  - `ledger done <id>` は `todo` の項目が残っていたら断る(下の問い 3)
- **ボード**:
  - TUI の工程表: 依頼の見出しに `#696 3/6` を足し、セッションの行の後に、まだ結んでいない項目を `○ 4 tapi への配送 · todo` と dim で並べる。`↵` で項目の全文、`dropped` は既定で畳む。Requests 区画の 1 件表示にも段取りを出す
  - Web UI の工程表: 同じものを読むだけで出す(2 本目の PR)
  - 概要の数は増やさない(`todo` は人の番ではない。人が見たいときに工程表で見る)
- **tapi の手順**(`skills/pekoe-orchestrate/SKILL.md` に書く):
  - 番号つきの案を出して、人が一部だけ選んだ・残りを後に回したら、案の全部を `ledger plan` で段取りにし、選ばれたものを `--request <id> --step <n>` で作る
  - 続きの依頼(「残りも進めて」)が来たら、`pekoe --json ledger` の段取りで番号を読み解き、元の依頼の項目に結ぶ。続きの依頼のほうは `ledger done <id> --note "#696 の段取り 4–6"` で閉じる(新しい親子の仕組みは作らない。困りごとの 4 のとおり、続きは今の仕組みで足りている)
  - リセットの後は、open の依頼の段取りを読んで続きから進める(会話を思い出さなくてよい)
  - 順序がある項目は、負荷の制御が入った後なら `--after` で先に作っておける。段取りは「やると決めたが、まだ作らない」もの(後に回した・時間のあるときに)の置き場所で、待ち行列(「作ったが、上限か `--after` で起動を待つ」もの)とは分ける
  - 自動の整理(U16)との関係: `ledger plan` もそのターンに「頼んだ」に数える(段取りだけ書いて後に回すターンの依頼を `chat` で閉じない)。`todo` の残る依頼は自動では閉じない
- **配送との関係**: 配送の 1 行に、段取りが進んだ依頼を `#696 4/6` のように添えられる(必須ではない)
- **コスト**: 中くらいの PR 1〜2 本(表 1 つ、メソッド 2〜3 個、CLI、TUI の表示、スキル、api.md、tips)。tapi のトークンは、段取りを書くときにコマンドが 1 回増えるだけ
- **危険**:
  - `todo` が溜まって放置される(段取りが「やる気のリスト」になる)。工程表に出ること自体が備えで、`ledger done` が `todo` を残したまま閉じないので、tapi か人がどこかで `drop` を選ぶことになる
  - tapi が段取りを書き忘れる。スキルの手順だけが頼りで、pekoed は文を読んで項目を作らない(依頼の記録と同じく、pekoed は文の中身を判断しない)
  - 項目の文はエージェントが書く。人が読む表示にだけ使い、ほかのセッションへの指示に流さない

### 案 C: プロジェクトと担当のセッションを作る(重い形)

U11 の (b)。「プロジェクト」(タイトル・完了条件・状態)を新しいものとして持ち、担当のセッションがそのプロジェクトのハブになる。tapi はプロジェクトごと担当に任せ、担当からの報告だけを待つ。

- **データの形**: state.db に `projects(id, title, goal, lead, status, created_at, closed_at)`。`Session.project`、`LedgerEntry.project` を足す。`lead` は担当のセッションの slug
  - 担当は、リポジトリが 1 つならそのリポジトリの main セッション。複数のリポジトリにまたがるなら、tapi と同じくデータディレクトリで動く新しい種類のセッション(`+tapi` に倣って `+lead-<id>` のような名前)が要る
  - 担当の中の段取りは、結局案 B と同じもの(項目の並び)が要る
- **CLI**(案): `pekoe project new "<タイトル>" --goal "<完了条件>" [--lead <slug>|--new-lead]`、`pekoe project [ls|<id>]`、`pekoe project close <id> --evidence …`、`pekoe new … --project <id>`
- **ボード**: ダッシュボードに「プロジェクト」の区画を足し、プロジェクトごとに完了条件・担当の状態・セッションの工程を出す。工程表のまとめ方に「プロジェクト」の段を足す(依頼元 → プロジェクト → 依頼)。Web UI にもプロジェクトの画面を足す
- **tapi の手順**: 大きな依頼はプロジェクトにして担当に `send` で任せ、担当の報告だけを `wait` で待つ。担当は pekoe-orchestrate スキルでセッションを作り(`parent` は担当の slug。今でも main をハブにする形で動く)、`--after` で順序を付け、済んだら tapi に報告する。人の判断が要るものは担当が `ask-human` で上げる
- **コスト**: 大きい。新しいもの(プロジェクト)と新しい役割(担当)、担当のための役割の指示・書けないようにする設定・スキル、ダッシュボードの区画、Web UI の画面。複数のリポジトリにまたがる担当は tapi と同じ作り(データディレクトリ・sandbox の設定・リセット)をもう 1 つ持つことになる。動かすときも、ハブが 2 段になるぶんトークンが増える(担当が待ち、まとめ、tapi がもう一度まとめる)
- **危険**:
  - 人が誰に話しかければいいか分からなくなる(tapi か担当か)。「話しかけるのは統括役 1 つだけ」という目指す体験から離れる
  - 報告が 2 回まとめられ、事実(SHA・evidence)が落ちる。受信箱の問いの依頼元が 2 段になり、答えがどこに戻るかが分かりにくい
  - 同時に動くエージェントが増え、負荷の制御の上限に早く当たる
  - 担当が自分で作業してしまう(tapi と同じ「自分で作業しすぎない」仕組みが担当にも要る)
- **今でもできる入口**: リポジトリが 1 つなら、tapi が main セッションに `send` で束ねて頼み、main がハブとして回す形は、コードを変えずに今でもできる(今あるセッションの 1 本がこの形)。足りないのは、main が作ったセッションを tapi の依頼に結ぶ道と、その完了条件の置き場所

## おすすめ

**案 B**。数えた結果では、複数 PR の大きなまとまりはまだ日常ではなく(2 本以上の依頼は 6 日で 16 件、最大 5 本、ほとんど 1〜2 日で済む)、担当のセッションを置くほどの量はない。一方で、tapi の会話にしかない段取り(番号で選ぶ依頼 16 件、後に回したもの 4 件、#696 と #697)は毎日起きていて、リセットで消える。B はこれを依頼の記録に残すだけで、人が話しかける相手も、今の工程表の形も変えない。C に進むときも、B の段取りはプロジェクトの中身としてそのまま使える。

C を考え直す目安(ledger と stats で数えられるもの): 5 本以上のセッションを結んだ依頼が週に 3 件を超える、`done` までに 2 日以上かかる依頼が週に複数ある、または段取りの `todo` が 10 項目を超える依頼が出てくる。

### 最初の 1 PR で作る範囲

- state.db の `ledger_steps` と、`LedgerEntry.steps`
- `ledger.plan`(項目を足す)・`ledger.step`(`done` / `dropped` / `todo` にする)、`session.new` と `ledger.link` の `step`。token なしでは tapi の窓から(今の `ledger.*` と同じ)
- `ledger.close` の `as: done` を、`todo` の項目が残っていたら断る(問い 3 の結果で変える)
- 自動の整理(U16): `ledger.plan` を「頼んだ」に数える。`todo` の残る依頼を閉じない
- CLI: `pekoe ledger plan` / `pekoe ledger step`、`pekoe new --step`、`pekoe ledger link --step`、`pekoe ledger <id>` と `--json` の表示
- TUI の工程表: 依頼の見出しの `n/m` と、`todo` の項目の dim の行
- `skills/pekoe-orchestrate/SKILL.md` の手順、docs/api.md の「依頼(ledger)」、`internal/tips/tips.toml` の tip(サブコマンドを足すので網羅テストが求める)

2 本目以降: Web UI の工程表に段取りを出す、配送の 1 行に段取りの進みを添える(配送が入った後)。

作らないもの: プロジェクトという新しいもの、担当のセッション、依頼の親子(続きの依頼は note で元の依頼を指す)、pekoed が依頼の文から段取りを推測すること。

   - (b) 1 つの依頼を 2 本以上のセッションに分けるときは毎回(工程表は揃うが、1 日で済む依頼にも書くことになり、tapi のコマンドが増える)
   - (c) 人が「段取りにして」と言ったときだけ(一番静かだが、後に回した項目は言い忘れると今と同じく消える)
3. **(B のとき)`todo` の項目が残った依頼を閉じるとき**
   - (a) `ledger done` を断り、tapi に残りを `done` か `drop`(理由つき)にさせる(おすすめ。後に回した項目が黙って消えない)
   - (b) 閉じられるが、残った `todo` を受信箱の `fyi` に 1 件出して人に知らせる
   - (c) 何もしない(閉じれば段取りも一緒に閉じる)

## 前提が変わったら

- **負荷の制御で `--after` が待たない形になった**: 段取りの項目に順序を持たせる必要が出るかもしれない。そのときは `ledger_steps` に `after`(先の項目の番号)を足し、tapi が先の項目の済んだのを見て作る(今の #696 の進め方)
- **負荷の制御が「まだ作らないセッション」(worktree なしの予約)を持つ形になった**: 段取りの `todo` と役割が重なる。その予約を段取りの項目として見せ、段取りの表は作らない形を考え直す
- **配送が入らなかった・形が変わった**: 案 B には影響しない(配送の 1 行に進みを添えるのは任意)
