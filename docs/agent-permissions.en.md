# Letting agents use pekoe: permissions

The long form of [Letting agents use pekoe: permissions](../README.md#letting-agents-use-pekoe-permissions) in the README.

Agents run as the same user, so they can connect to pekoed's socket. pekoed runs outside the agents' sandbox, so without the `human-token` it allows only what agents need: `pekoe event` from the hooks, `pekoe ls`, `pekoe new`, `pekoe send`, `pekoe land`, `pekoe rm`, `pekoe wait`, `pekoe reports`, `pekoe inbox` (the list), `pekoe stats` (counts only), `pekoe conflicts` and `pekoe cleanup` (the list; it reads git status in the worktrees at most every 10 seconds each) for the hub (the skill; `send` only into an agent's input box and not while it shows a permission dialog; `land` only in a repository with an origin; `rm` only of a landed session, below), `pekoe ledger` for tapi chat (the list, closing, linking and keeping; only from tapi's window), `pekoe report` and `pekoe dev` for a working session (its own session only), `pekoe ask-human` for an agent asking a person (only a person answers; it can `withdraw` its own question), and the MCP server's `session_list` and `open_in_editor`. Everything else (answering permission prompts, raw keys, typing into tapi chat, drafting and writing settings, starting another session's `dev`, running commands in the run window or the review surface, looking at other sessions' screens, diffs or error excerpts, stopping the daemon, …) needs the token. `rm` without the token removes only a landed session: when pekoed saw its PR merged it already ran the teardown and removed the worktree, so what is left is pekoe's record of it and the code is on the base branch. `rm` of a session in any other state would delete a worktree and its uncommitted changes, so it stays human-only, and so do `rm --force` and a landed session whose worktree is still there (its removal failed). The token is in `~/.local/share/pekoe/human-token` (`$PEKOE_HOME/share/human-token` if `$PEKOE_HOME` is set; mode 0600), and the TUI, CLI and Neovim read it and send it. Neither the token nor its path is put in the environment of the agents' panes. Which method is which is listed under "人間だけの操作" (human-only operations) in [docs/api.md](api.md).

But an agent running as the same user can read files. Two things keep the token from it:

1. **Claude Code agents run in a Claude Code sandbox that pekoe configures (on by default).** Every time pekoe starts Claude Code (new sessions, `open`, restarts, resuming after a daemon restart, and tapi chat; any `[agents.*]` whose `command` starts with `claude`), it adds `--settings <data dir>/agent-settings/<slug>.json`. The paths in it are the real ones, following `$PEKOE_HOME`, `$XDG_DATA_HOME`, `$XDG_CONFIG_HOME` and `[web] state_dir`:
   - `sandbox.enabled: true`, `allowUnsandboxedCommands: false` (no retry with `dangerouslyDisableSandbox`), `failIfUnavailable: true` (Claude Code doesn't start without a working sandbox), `filesystem.disabled: false`
   - `filesystem.denyRead`: `human-token`, `http-token`, `state.db` (with `-wal` and `-shm`: it holds prompts, review comments, reports and the send log, which agents read only through pekoed's API), the tsnet state, the local GUI's sign-in pages (`~/.local/share/pekoe/gui/`), pekoe's config directory (`~/.config/pekoe`) and the profiles of the common browsers (Chrome, Edge, Brave, Arc, Firefox, Safari …: the local GUI's session token may be written there; on Linux only those present when the agent starts). Enforced at the OS level for Bash commands and their children
   - `permissions.deny`: `Read(...)` and `Edit(...)` for the same paths (the Read and Edit tools run outside the sandbox), and `Edit(...)` for `agent-settings` itself and the written skills' text (`skills/`)
   - `permissions.allow`: `Read(...)` for the directory of images sent to this session from the Web UI (`<data dir>/images/<slug>/`, tapi chat's `images/+tapi/`), so the agent opens the `[image] <path>` lines of a send without asking ([docs/web.md](web.md), 「画像の扱い」)
   - `filesystem.denyWrite` and `Edit(...)`: the repository's `.git/config`, `.git/config.worktree` and `.git/hooks`, and the same in the git directories of its submodules (`.git/modules/…`, those there when the agent starts) (agents can still commit, but can't change settings the git you run yourself follows)
   - tapi chat only: `filesystem.denyWrite` and `Edit(...)` for each repository it reads through `--add-dir` and for `~/worktrees` (symlinks resolved too). The orchestrator hands work to sessions instead of doing it, so it can't write there with Bash, Edit or Write. Its own directory (`tapi/`) stays writable. `[agents.<tapi's agent>] sandbox = false` drops this as well
   - `network.allowUnixSockets`: pekoed's socket (for `pekoe ls`, `new` and `send`). Hooks run outside the sandbox, so `pekoe event` isn't affected anyway
   - `hooks.MessageDisplay`: only when, at the agent's start, `[voice] enable = true` and `focus_mode` or `background_mode` is `read`. `<pekoe's absolute path> event MessageDisplay` (2-second timeout) hands the reply's text to pekoed as it is shown ([docs/voice.md](voice.md), 3.1). It runs alongside the hooks in `~/.claude/settings.json` (they are merged). An agent with `sandbox = false` still gets a file with this hook alone

   **Claude Code only.** codex, opencode and other agents get nothing; if you use them, make the same paths unreadable with their own sandbox. `[agents.claude] sandbox = false` in `config.toml` turns it off (per agent definition, e.g. `[agents.claude-ask]`).

   **How it combines with your own settings** (Claude Code's [sandbox](https://code.claude.com/docs/en/sandboxing) and [settings](https://code.claude.com/docs/en/settings) docs; this can change between versions):
   - `--settings` ranks above `~/.claude/settings.json` and a repository's `.claude/settings.json` (only managed settings rank above it). `"enabled": false` in `~/.claude/settings.json` doesn't turn the sandbox off in pekoe's sessions
   - Lists such as `denyRead`, `allowWrite`, `allowedDomains` and `permissions.deny` are merged: yours are added to pekoe's
   - Because `allowUnsandboxedCommands: false` comes from `--settings`, the sandbox is "admin-required": settings that loosen it count only from `--settings`, `~/.claude/settings.json` and managed settings. `allowWrite`, `allowedDomains`, `excludedCommands` and the like in a repository's `.claude/settings.json` / `.claude/settings.local.json` are ignored (agents can write those files)
   - `excludedCommands` in `~/.claude/settings.json` do apply, and the commands listed there run outside the sandbox, where they can read the token. Don't list commands that can read files (`gh`, `cat`, `python`, …), and don't reopen the paths above with `filesystem.allowRead`

   **What stops working by default:** writing outside the working directory (the worktree), the temp directory and `--add-dir` directories (the Go build cache, npm / pnpm caches, …), and network access to domains you haven't allowed (none at first; auto mode refuses them, manual permission modes ask). `git commit` works (the worktree's shared `.git` is writable). To loosen it, put only `allowWrite` / `allowedDomains` and the like in `~/.claude/settings.json`. Without `"enabled"` they don't affect Claude Code outside pekoe (its sandbox stays off there). An example, with what developing pekoe itself needs (Go's caches and modules, `gh`; npm only if you use it):

   ```json
   {
     "sandbox": {
       "enableWeakerNetworkIsolation": true,
       "filesystem": {
         "allowWrite": ["~/Library/Caches/go-build", "~/go/pkg/mod", "~/.npm", "~/Library/pnpm/store"]
       },
       "network": {
         "allowedDomains": ["proxy.golang.org", "sum.golang.org", "github.com", "api.github.com", "registry.npmjs.org"]
       }
     }
   }
   ```

   Check the paths with `go env GOCACHE GOMODCACHE`, `npm config get cache` and `pnpm store path` (on Linux, `~/.cache/go-build` and so on). In the macOS sandbox `gh` fails to verify TLS (`x509: OSStatus -26276`); with `enableWeakerNetworkIsolation: true` and `api.github.com` allowed it works (tested). Don't put `gh` in `excludedCommands` to run it outside the sandbox (`gh api --input <file>` could send the token out). If you don't loosen it, a person handles issues in the TUI (the same goes for tapi chat's counts that use `gh`), and `pekoe land` becomes the agents' way to push: pekoed pushes and opens the PR, after running the tests in its own sandbox. If you do allow `github.com` / `api.github.com`, an agent can `git push` and `gh pr create` by itself anyway, which is why `land` is open to agents; what keeps you in control is that you merge.

   With `--permission-mode bypassPermissions`, connections to domains you haven't allowed go through without asking (Claude Code's behavior), so the network restriction has practically no effect; the file restrictions (the token stays unreadable) remain. On Linux, Claude Code's sandbox needs bubblewrap and socat; without them `failIfUnavailable` keeps Claude Code from starting (the agent's window shows why).

   After reinstalling, have an agent try `cat ~/.local/share/pekoe/human-token` and `pekoe answer no-such-session deny`, and check that the first fails with `Operation not permitted` and the second is refused with `only a person can do this` (not `no such session`).

2. **Don't allow pekoe wholesale, as in `Bash(pekoe *)`.** The hub (the pekoe and pekoe-orchestrate skills) uses `ls`, `new`, `send`, `wait`, `reports`, `inbox`, `conflicts` and `cleanup` (the list; tapi also `ledger`), and a working session (the pekoe-work and pekoe-review skills) uses `report`, `ask-human` and `dev` (to look at its UI), so if you add pekoe to the allow list, limit it to those. `pekoe inbox answer` and `pekoe ledger reopen` / `rm` are a person's operations and are refused even if you allow them. Don't add `pekoe event` (for hooks), `answer`, `init`, `rm` or `daemon`. Without the token, `dev` only starts or stops the dev server of the calling session (its own window) and refuses another session's slug (what runs is the repository's `[hooks] dev`, in pekoe's own sandbox like `[hooks] test`). `land` works without the token, but leaving it off the allow list makes Claude Code ask you before each push. The same goes for `rm`: an agent can clear a landed session, and Claude Code asks you first

   ```json
   {
     "permissions": {
       "allow": [
         "Bash(pekoe ls)", "Bash(pekoe --json ls)", "Bash(pekoe --json new *)", "Bash(pekoe send *)",
         "Bash(pekoe report *)", "Bash(pekoe --json reports *)", "Bash(pekoe --json wait *)",
         "Bash(pekoe --json ask-human *)", "Bash(pekoe --json inbox)", "Bash(pekoe --json inbox *)",
         "Bash(pekoe --json ledger)", "Bash(pekoe ledger *)", "Bash(pekoe --json stats *)",
         "Bash(pekoe --json conflicts)", "Bash(pekoe --json conflicts *)", "Bash(pekoe --json cleanup)", "Bash(pekoe dev *)"
       ]
     }
   }
   ```

**Commands from a worktree run in pekoe's own sandbox.** pekoed runs commands that come from code an agent can change: `[hooks] test` after every Stop, the `[review] gatekeeper`, `setup` on `pekoe new`, `dev` and `dev_stop`, `teardown` on rm / land, and the tests of `land`. Anyone can report a Stop, so an agent could otherwise put `cat ~/.local/share/pekoe/human-token` in a Makefile and have pekoed run it outside the agent's sandbox. pekoed runs these in a sandbox: `sandbox-exec` (Seatbelt) on macOS, bubblewrap (`bwrap`, from your distribution's package) on Linux. Everything is allowed (builds, tests and dev servers work as before) except reading `human-token`, `http-token`, the tsnet state, `config.toml`, `state.db` and the common browsers' profiles (where the local GUI's session token may be written; on Linux only those present when the command starts); writing pekoe's data and config directories and files that run later outside it (shell startup files, `~/.gitconfig`, launch agents, the writable directories on `$PATH`, what the next Claude Code reads and runs: `~/.claude.json`, and `settings*.json`, `skills`, `hooks`, `plugins`, `agents`, `commands`, `rules`, `output-styles` and `CLAUDE.md` in `~/.claude` or `$CLAUDE_CONFIG_DIR`, …); connecting to tmux servers and to the review surface's nvim (pekoe starts it with `--listen` in its data directory); and, on macOS, opening apps or sending Apple events. Where no sandbox works, pekoe doesn't run them: the session shows `test not run: no sandbox`, the gatekeeper's reason shows up among the risks, and setup / dev / teardown / land fail saying why. `[sandbox] enable = false` in `config.toml` runs them without one. On Linux, bwrap can only cover paths that exist, so before running a command pekoed makes the missing ones that change nothing by being there empty (in `~/.claude` / `$CLAUDE_CONFIG_DIR`: the directories above as empty directories, an empty `CLAUDE.md`, `settings*.json` of `{}`; empty `~/.config/git`, `~/.config/nvim` and the like), and for the rest (shell startup files you don't have, `~/.claude.json` …) makes their nearest existing parent read-only, with what is in it now still writable: in practice, a command can't create new files or directories directly in your home (it can still write inside the existing ones). Not wrapped: the run window (`!`, a command you type yourself) and the agents (their own sandbox's job). The deny list is aimed at the secrets: a command can still write elsewhere in your home, so this doesn't replace reviewing what an agent changed. Two known gaps, left open so your tools keep working: such a command can write the repository's own `.git/hooks` and `.git/config` (husky, pre-commit and lefthook install themselves there from `npm install` or a setup step), which the git you run in the main checkout then follows outside any sandbox — pekoed watches them (and the directory `core.hooksPath` points at) around each of these commands and, when hooks or settings that name a command (`core.hooksPath`, `core.fsmonitor`, `alias.*`, `include.path`, …) changed, puts an item in your inbox saying what changed, in which session and during which hook (it changes nothing itself); and it can connect to other unix sockets such as Docker's or ssh-agent's. Details: [docs/api.md](api.md) ("hooks の sandbox", "本体の .git の見張り").

**pekoed's own git doesn't run what an agent wrote into git's config.** git runs commands named in its config (`core.fsmonitor` on every `git status`, hooks, credential helpers, filter and merge drivers picked by `.gitattributes`, `gpg.program`, `core.sshCommand`, …), and pekoed runs git in the worktrees all the time (diffstat, snapshots, review, undo, the conflict forecast, land, rm). An agent can rewrite its worktree's `.git` file to point at a git directory of its own, and an agent that can commit can usually write the repository's `.git` too. So pekoed (and the `gh` it runs) uses the git directory the repository has for each session's worktree, whatever its `.git` file says (if that file was changed, pekoe runs no git there and the session shows `.git changed: git stopped`); sets the settings that name a command from your own config (system / global) or git's defaults — no fsmonitor, no hooks at all (so `land`'s push runs no pre-push hook), only your credential helpers and signing programs, no `ext::` remotes, `--no-ext-diff --no-textconv`, the default upload-pack / receive-pack; and runs git in the same sandbox as the hooks, for what has no fixed name (filter and merge drivers, git-lfs settings, the hooks of a local-path remote). Where no sandbox works, git still runs (pekoe can't work without it) and those last ones are not contained. git you run yourself (your shell, the run window, git plugins in the review surface's nvim) reads the worktree as git normally does: check `.git` before using git in a worktree that shows the warning, and don't let agents write `<repo>/.git/config` or `.git/hooks` (pekoe passes `sandbox.filesystem.denyWrite` and `Edit(...)` denies for them to Claude Code agents; block them yourself for other agents). Commands pekoed runs from a worktree can still write them (above); look at the inbox item pekoed posts when they changed before using git in the main checkout. Details: [docs/api.md](api.md) ("pekoed が動かす git").

The Web UI and the Chrome extension are human entry points that don't go through the socket, so each works with its own authentication. Threat model: [docs/web.md](web.md#脅威モデル).
