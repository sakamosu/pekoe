# ローカル GUI のデザイン原則

ローカル GUI(docs/gui.md、`internal/daemon/webui/gui/`)の見た目の基準。段階 1 の見た目は仮で(docs/gui.md の冒頭)、最終的な見た目はこの文書に照らして別の PR で作り、レビューする。

**状態**: 原則の文書の PR で挙げた未決事項 12 件は、末尾の「決まったこと」のとおりユーザーが決めた(2026-11-21)。見た目はこの文書に沿って実装した(`internal/daemon/webui/gui/`・`/theme.css`)。実装で決めたこと・データが無くて出していないものは末尾の「実装で決めたこと」に書いた。

根拠はファイル名で添える。「モック」はユーザーが作ったデザインのモック(Dashboard・Session・Session states の 3 枚、2026-11-21。リポジトリには入れていない)と、そのハンドオフの文書を指す。モックの寸法と色は inline style から読んだ。コードと docs で確かめたことと、推測(「推測」「要確認」と書く)を分ける。

## 置き場所: 別の文書にした

`docs/ui-guidelines.md` に節を足さず、この文書を別に置いた。理由:

- ui-guidelines.md は端末という媒体の上の原則で、半分以上が端末の事情(セル幅、truecolor / ansi / none の 3 モード、Nerd Font、box-drawing、powerline のキャップ、曖昧幅)でできている。GUI はそのどれも持たず、代わりにフォント・ピクセルの余白・角丸・ライトモード・ブラウザのフォーカスを決める必要がある。同じ文書に混ぜると、各規則が TUI だけか両方かを毎回書き分けることになる
- 色の理屈(OKLCH・明度とクロマを揃える・色相は 5 つ・面積の規律)とトークンの役割は両方に効く。これは ui-guidelines.md を正とし、この文書は「引き継ぐ」と書いて参照するだけにする。値を二重に持たない(ダークの hex は ui-guidelines.md、GUI で足す役割とライトの列だけここ)
- 読み分け: **TUI と共通の原則は ui-guidelines.md、GUI だけの原則と GUI で変えるものはこの文書。** 迷ったら ui-guidelines.md の「判断に迷ったら」の 4 つに戻る点は同じ

## TUI から引き継ぐもの

ui-guidelines.md のうち、そのまま GUI にも効くもの。この文書で上書きしない限りこちらが正。

1. **色が付いていたら必ず意味がある。** 装飾の色を置かない。色は状態・データ・操作(フォーカス・キー・警告)にだけ
2. **派手さは面積ではなく彩度で出す。** ネオン(primary / secondary / warn / ok / err)の面積は画面の 10% 以下。ネオンで 2 行以上の文章を書かない
3. **色の作り方。** OKLCH で設計し、アクセントは明度とクロマを揃える。色相は 5 つ+無彩色から増やさない。新しい色は既存の役割の L/C の派生で作る。背景は冷たい低クロマで、`#000` / `#fff` を使わない
4. **コントラストの下限。** 本文 7:1 以上、アクセントと dim の文字 4.5:1 以上(下の「コントラスト」で GUI の地ごとに計算した)
5. **状態の語彙。** 状態の記号・色・語は ui-guidelines.md の「状態の表現」の表のまま(◉ ok 稼働中、◉ warn 確認待ち、◦ dim 待機、◌ 作成中、✓ secondary 完了、✗ err 失敗 …)。確認待ちは warn に固定する
6. **フォーカスは 1 つ。** 画面の中で「いま人が扱うもの」を示す強い表現は 1 つだけ(GUI での定義は下の「フォーカス」)
7. **キーの表し方。** `key action` の形。key は secondary、action は英小文字の短い語句(ボタンでは文頭大文字。下の「ボタン」)。同じ意味には同じキー(n 新規、D 削除、`?` ヘルプ、`:` コマンド)
8. **凝った表現は枠に、内容は素のまま。** アイコン・塗り・グラデーションはクローム(タイトルバー・サイドバー・タブ・ステータスライン・カードの枠)に置き、エージェントの出力・差分・報告の本文には入れない
9. **実行対象は bg に沈めた 1 行。** コマンド・パス・ブランチ・HEAD のように「何に対して起きるか」は、全幅 1 行で bg の地に沈めて見せ、その行に色文字を置かない(ui-guidelines.md の「チュートリアル」の節の規則。モックの Inbox カードの `pekoe · feat-local-gui-stage0 · HEAD ae73672`、許可カードのコマンドの行)
10. **破壊的な操作は確認を通す。** 取り返しのつかない操作のキーは err の色(モックの `n Deny`)
11. **動きは意味があるときだけ。** スピナー以外は動かさない。フォーカスのグラデーションも静止
12. **表示の言語。** 画面の文言は英語(ui-guidelines.md の「実装ルール」)。データ(エージェントの文・依頼の本文)はそのまま

## GUI で変えるもの

ハンドオフの「設計を考え直す点」1〜10 を GUI の原則として書き直したもの。どれもユーザーがモックを見て選んだ結果なので、決まったこととして書く。後から決めた部分は、末尾の「決まったこと」の番号を添える。

| # | 決まったこと | TUI(ui-guidelines.md)との違い | 理由・根拠 |
| --- | --- | --- | --- |
| 1 | **書体はプロポーショナルの 1 系統に統一する。** まず OS の UI 書体(system-ui。Mac ではラテン文字が SF Pro、日本語がヒラギノ)で組み、許容できなければ Inter の同梱を検討する(決まったこと 2)。数字は tabular figures(`font-variant-numeric: tabular-nums`)。等幅はエージェントの画面と実行対象の行だけ(決まったこと 1) | TUI は端末の等幅フォントしかない | モックの全画面が `Inter, 'Noto Sans JP', system-ui, sans-serif`。経過時間・件数・diff の増減が並ぶので桁を揃える。モックの Inter はまず使わず、外から読まない system-ui で組む(決まったこと 2)。エージェントの画面は桁がそろわないと崩れるので等幅に戻す(決まったこと 1) |
| 2 | **フォントを外から読まない。** まず system-ui(同梱しない)。Inter の同梱は代案(決まったこと 2) | (TUI には無い) | モックは Google Fonts から読んでいるが、GUI の CSP(`default-src 'self'; style-src 'self'`、`internal/daemon/web.go` の `webCSP`)は外のスタイルシートもフォントも断る。docs/web.md も「外部 CDN・フォントは読まない」 |
| 3 | **グラデーション(primary → primary_end)は 2 か所だけ: Dashboard の Inbox カードの枠と、Session の送信欄の枠(待っている間は、送信欄の代わりに出る許可・質問のカードの枠。決まったこと 10)。** タブの選択と開いている行は primary 単色。文字には使わない | TUI はフォーカス中のパネルの枠とモーダルの枠がグラデーションで、「カードに primary の枠は使わない」 | GUI にはパネルの枠線がほぼ無く(区画は見出しと罫線)、「パネルのフォーカス」で強調するものが無い。代わりに「その画面で人が次に扱うもの」をカードの枠で示す(下の「フォーカス」)。モックの `--focus` が使われているのはこの 2 か所だけ |
| 4 | **bubble_me(自分の吹き出しの地)は primary_end の派生 `#1c2c51`(OKLCH 0.30 / 0.07 / 265)。** primary_end の「役割を持たない」に、吹き出しの地を例外として足す | TUI(と今の Web UI)は secondary の派生 `#003643` | `#003643` は深緑に見えて不評だった(ハンドオフ)。select が primary の影なのと同じく、primary_end の影にした。iPhone の Web UI も同じ色に変える(決まったこと 9) |
| 5 | **ライトモードを入れ、テーマを切り替えられるようにする。** ライトのトークンは下の表 | TUI は「ダークのみ対応」 | ブラウザは OS の外観に合わせるのが普通で、明るい部屋で使う人がいる。モックはダーク・ライトの両方を描いた。出し方と切り替えの記憶は決まったこと 11 |
| 6 | **状態は記号・色・語でそろえる。** ダッシュボード本体と Session はモックどおり、サイドバー(たたんだ行も)にも 3 つをそろえる(決まったこと 3) | TUI は「3 つが常にそろう」 | モックのサイドバーは `Ready to merge`・`done · 7d` のように語と色だけの行と、`◉ Running`・`✗ failed · 4d` のように記号のある行が混ざっている |
| 7 | **パネルに番号(`[1]`〜`[4]`)を出さない。** 左端のアイコンレール(Sessions / Worktrees / Changes、下に Settings)と、メインのタブ(Dashboard・tapi・開いたセッション)で切り替える | TUI はタイトル行が `[n] 名前 位置 状態` で、数字キーで直接フォーカス | マウスで使う人には番号より形と名前の方が速い。数字キーでの移動は残さず、数字は質問カードの選択肢に使う(決まったこと 4) |
| 8 | **区画の見出しに絵文字を使わない。** 見出しは「太字の名前+件数+罫線」 | TUI のダッシュボードは「絵文字 1 つ+太字の名前+罫線」(ui-guidelines.md の「ダッシュボードの例外」) | 端末で絵文字が担っていた「どこを見ればいいか」は、GUI では大きさ・太さ・カードの枠で出せる。見出し以外(空の表示の一言など)はモックに例が無いので、迷ったら使わない(推奨) |
| 9 | **ネオンの塗りはステータスラインのモードのピル 1 つだけ。** 主ボタンの地は select | TUI と同じ(唯一の例外がモードセグメント) | 面積の規律。主ボタンをネオンで塗ると画面にネオンの面が増える。select は primary の影なので「押すならこれ」が色族のまま伝わる |
| 10 | **ボタンは `key action` の形。** キーは secondary の太字、続けて動詞。キーの割り当ては仮のものが混ざる(下の「仮のもの」) | TUI のキーヒントと同じ形をボタンの中に持ち込んだ | マウスの人もキーを目で覚えられ、TUI と GUI を行き来しても同じキーで済む |

ほかにモックから読み取れる、TUI と違うもの(ハンドオフの 1〜10 には無いが、モックで一貫している):

- **選択の地は select ではなく raised。** 開いている行・選択中のチップ・レールのボタンは無彩色の raised で塗り、開いている行は左に primary の 2px のバーを添える。select は主ボタンとステータスラインのセグメントに回した(TUI では select は選択行の地)。推測: 主ボタンと開いている行が同じマゼンタの影で張り合わないため
- **太字の段階を使う。** TUI は「太字はフォーカス中のタイトルとキー文字だけ」だが、モックは 400(本文)・500(名前・表の見出し)・600(見出し・タイトル・主ボタン)・700(キー文字)の段階で構造を出している(下の「タイポグラフィ」)
- **小さな大文字のラベル。** サイドバーと右パネルの区画名(`SESSIONS`・`OTHER REPOSITORIES`・`USAGE`・`BACKGROUND`)は 11px・600・字間 0.08em・dim の大文字

## カラートークン

コードから参照するのは役割名だけ(ui-guidelines.md の「役割ベースのテーマ」)。GUI の CSS では `var(--<役割>)` で、hex は `/theme.css`(`internal/daemon/web.go` の `webThemeCSS`)だけが書く。

- **chrome と raised** は bg と同じ色相 285 の無彩色の派生(ダークは L0.22 と L0.29、C0.03)。色相を足さないので「派生色は同一色相で L と C を落とす」の範囲に入る。段は ダーク `bg 0.20 < chrome 0.22 < surface 0.24 < raised 0.29 < border 0.36`。ライトは `raised 0.91 < chrome 0.95 < bg 0.97 < surface 0.99` で、chrome が bg より暗く、カード(surface)が一番明るい(紙が浮く向き)
- **primary_end の例外**: ui-guidelines.md の注記「primary_end は役割を持たない」に、「bubble_me の色相の元にする」を足す。bubble_me は primary_end を select と同じ深さ(ダーク L0.30・C0.07)に落とした影で、吹き出しの地として面で出るが、文字・記号・枠には使わないので、bubble_me については「単独の文字や記号に使うことは禁止」は保たれる。code(吹き出しのインラインコードの文字)はこれと違い、primary_end の色相を文字に使う唯一の例外で、ui-guidelines.md の同じ注記に断り書きを足した(ダークは primary_end と同じ L0.78・C0.09、ライトは他のアクセントと同じ L0.50 の #3e5fad)。色相 265 は secondary(215)から 50° 離れており、キー文字のシアンと取り違えない(ui-guidelines.md の primary_end の説明と同じ理由)
- **導出**: 今の `theme.BubbleMe`(`internal/theme/web.go`)は secondary から計算している。primary_end から計算するように変える(実装の PR)。primary だけを上書きして primary_end が無いとき(単色の枠)は、既定の primary_end の色相 265 を使う(推奨。select と同じ色相にすると「押せるもの」と見分けにくい)
- **グラデーション**: `linear-gradient(to bottom right in oklch, var(--primary), var(--primary-end))`。方向は TUI と同じ左上 → 右下。`in oklch` の補間に対応しないブラウザでは primary 単色の枠に落とす(`@supports` で切り替える。推測: 対応は Chrome 111・Safari 16.2・Firefox 127 前後から。要確認)。primary_end が無い(単色の設定)ときも primary 単色

### コントラスト

WCAG 2.x の相対輝度で計算した(sRGB の hex から。スクリプトはリポジトリに入れていない)。太字は 4.5:1 を割るもの。

**ライト**(ハンドオフの「bg と chrome のどちらに対しても 4.5:1 以上」を確かめた。primary_end は文字に使わないので下限の対象外):

| 文字 | 対 bg | 対 chrome | 対 surface | 対 raised |
| --- | --- | --- | --- | --- |
| text | 14.6 | 13.6 | 15.5 | 12.2 |
| dim | 5.5 | 5.2 | 5.9 | 4.6 |
| primary | 5.0 | 4.6 | 5.3 | **4.2** |
| secondary | 5.3 | 5.0 | 5.6 | **4.4** |
| warn | 5.2 | 4.9 | 5.5 | **4.4** |
| ok | 5.1 | 4.8 | 5.4 | **4.3** |
| err | 5.2 | 4.8 | 5.5 | **4.3** |
| (primary_end) | 4.49 | 4.2 | 4.8 | 3.8 |

- 対 bg・chrome・surface はすべて 4.5:1 以上で、ハンドオフの計算は正しい。いちばん低いのは primary の対 chrome 4.64
- **対 raised はアクセントがどれも 4.5:1 を割る(4.2〜4.4)。** モックでは開いている行(raised)に `Ready to merge`(secondary)と diff の `+1604 −95`(ok / err)が乗っているので、ライトではここが下限を割る。そこで raised の上では語を text にし、色は記号だけに持たせる(決まったこと 12)
- select の上: text 12.4、キー文字の secondary 4.50(ちょうど下限)、err 4.4(Deny を主ボタンにしない限り select の上には乗らない)
- bubble_me の上: text 12.6、dim 4.8
- code(インラインコード)は地の bg の小箱の上: 5.6(対 surface 5.9・対 bubble_me 4.8 なので、小箱の外に出ても下限に入る)。ダークは対 bg 9.1・対 surface 8.3・対 bubble_me 6.8。secondary との輝度比は 1.05 で明るさでは分かれないので、色相(265 と 215)と小箱・等幅で見分ける
- モードのピル(primary の地に bg の文字): 5.0

**ダーク**(ui-guidelines.md の値は対 bg。GUI で足した地に対して計算し直した):

| 文字 | 対 bg | 対 chrome | 対 surface | 対 raised |
| --- | --- | --- | --- | --- |
| text | 13.9 | 13.2 | 12.6 | 10.9 |
| dim | 5.0 | 4.7 | 4.5 | **3.9** |
| primary | 8.4 | 8.0 | 7.7 | 6.6 |
| secondary | 9.5 | 9.1 | 8.7 | 7.4 |
| warn | 11.2 | 10.6 | 10.2 | 8.7 |
| ok | 9.7 | 9.3 | 8.9 | 7.6 |
| err | 6.8 | 6.5 | 6.2 | 5.3 |

- **dim は raised の上で 3.9:1** に落ちる。モックの開いている行の経過(`7m`)と PR 番号(`#251`)は dim なので、ダークではここが下限を割る(決まったこと 12 で、raised の上では dim を使わない)。dim の対 surface は 4.51 で下限ちょうど
- dim は select の上でも 3.8:1(TUI の選択行と同じ事情)。bubble_me の上の dim は 3.7:1 なので、**吹き出しの中に dim の文字を置かない**(モックは差出人と経過を吹き出しの外に出している。それに合わせる)
- 枠線・バー・ゲージのような文字でない部品(WCAG 1.4.11 は 3:1): primary の 2px のバーは対 raised でダーク 6.6・ライト 4.2、タブの上辺は対 bg 8.4 / 5.0 で足りる。border は対 bg 1.7(ダーク)・1.5(ライト)で 3:1 に届かないが、TUI と同じく枠線は飾りの区切りで、ボタンは文字(ラベル)で見分けられるので下限の対象にしない

パレットを変えるとき(ユーザーの `[theme.colors]` を含む)は、GUI の地(chrome・surface・raised)に対しても計算し直す。

## タイポグラフィ

- **書体**: 本文から見出し・ボタン・表まで 1 系統(上の 1)。指定は `system-ui, -apple-system, "Hiragino Sans", "Noto Sans CJK JP", "Noto Sans JP", sans-serif` で、何も読み込まない(決まったこと 2)。等幅(`--mono`)は Screen と、bg に沈めた実行対象の行(コマンド・パス・SHA)だけ(決まったこと 1)
- **大きさ**(モックで使われているもの): 11px(メタ情報・区画のラベル・ステータスライン)/ 12px(補助の行・小さいボタン・表)/ **13px(本文の基準、行の高さ 1.5)** / 14px(タイトルバーの `pekoe`)/ 15px(セッションのヘッダの名前)/ 16px(件数の数字)/ 18px(Inbox カードの見出し)/ 24px(Overview の大きな数字)。新しい大きさを足す前に、この 8 段で済まないかを問う
- **太さ**: 400 本文 / 500 名前・表の見出し・強調したい数字 / 600 区画の見出し・カードの見出し・主ボタンの語・モードのピル / 700 キー文字だけ。TUI の「太字はタイトルとキー文字だけ」を、GUI では「段階は 4 つ、700 はキー文字だけ」に置き換える
  - 注: モックは Google Fonts から 400・500・600 だけを読み、700 はブラウザの合成か代替の書体で描かれている(推測)。system-ui(SF Pro・ヒラギノ)は 4 つの太さを持つ。代案の Inter を同梱するときは 700 も入れるか、キー文字を 600 にする
- **数字**: tabular figures を全体に掛ける(モックの最上位の `font-variant-numeric: tabular-nums`)
- **大文字のラベル**: 11px・600・字間 0.08em・dim。サイドバーと右パネルの区画名だけ。メインの区画の見出し(Inbox・Overview・Pipeline・Requests)は文頭だけ大文字の 13px・600
- **色**: 本文は text、補助は dim。ネオンで文章を書かない(TUI と同じ)。色付きの文字は状態語・キー・リンク・数字の強調(`1 to merge` の 1)まで
- **イタリック・下線・点滅は使わない**(TUI と同じ)。リンクは下線なしの secondary で、hover で text(モックの `a:hover`)

## 余白・寸法・角丸

細かい寸法はモックを正とする。ここには原則に関わるものだけを書く。

- **4px の格子**: 間隔は 2・4・6・8・10・12・14・16・20・24・28px から選ぶ。メインの区画の内側は 24px、区画どうしは 28px、カードの内側は 16〜20px、カードの中の要素は 10〜14px
- **高さの段**(押せるもの): 40px(主な操作のボタン: Merge・Allow・質問の選択肢)/ 36px(送信欄のボタン、サイドバーのたたんだ行)/ 32px(タイトルバーのボタン・検索欄、キー列)/ 28px(フィルタのチップ・Refresh・Manage のような小さい操作)。28px を押せるものの下限にする(デスクトップのマウス向け。iPhone の Web UI は 44px のまま)
- **角丸は大きさで決める**: 2px(棒グラフ・ゲージ)/ 4px(キーの小さな枠)/ 6px(ボタン・行・入力欄・沈めた行)/ 8px(主な操作のボタン・吹き出し・サイドバーのカード)/ 10px(カード・区画の枠・表の枠・ピル)/ 高さの半分(チップ。28px なら 14px)。同じ種類の部品に違う角丸を混ぜない
- **幅**: アイコンレール 48px、サイドバー約 300px、Dashboard の tapi パネル約 340px、Session の右パネル約 300px、メインは 520px 以上。狭くなったら横の列を下に回し(モックは `flex-wrap`)、**メインは消さない**(TUI の「メインパネルは消さない」と同じ)
- **影・ぼかし・背後を暗くする効果は使わない。** 段差は地の明るさ(bg・chrome・surface・raised)と枠線で出す(TUI の「背後を暗くしない」と同じ考え)。モックの選択中のタブにある `box-shadow: 1px 0 0 var(--border)` は影ではなく右の区切りの線なので、実装では border で描く

## ボタン

- **形**: `key action`。キーは secondary・700、続けて動詞を文頭大文字で(`↵ Merge #251`、`o Open evidence`、`⌘↵ Send`)。キーの無いボタンは動詞だけ(`View diff`・`Reply to tapi`)。TUI のキーヒント(英小文字)と違い、ボタンの中だけ文頭を大文字にする(モックがそうなっている。ステータスラインのキーヒントは TUI と同じ英小文字)
- **主ボタン**: 地は select、枠なし、語は text・600。**1 つのまとまり(カード・送信欄)に主ボタンは 1 つ**(モックの Merge、Allow once、Send)
- **副ボタン**: 地なし、border の 1px の枠、語は text(重要度の低いものは dim)
- **破壊的な操作**: 地や枠を err にせず、キー文字だけ err にする(モックの `n Deny`)。主ボタンにしない。TUI と同じく確認を通す(GUI の確認シート。docs/gui.md の MVP)
- **ネオンで塗らない**: ボタンの地に primary・secondary・warn・ok・err を使わない(上の 9)
- **diff の増減をボタンに添える**ときは ok / err の数字だけ(`View diff +1604 −95`)

## 状態の表し方

- **語彙は TUI と同じ**(ui-guidelines.md の「状態の表現」)。GUI の新しい状態はハンドオフの「鮮度」と「送達」で、既存の記号と色に当てる:

  | 表示 | 記号 | 色 | 意味 |
  | --- | --- | --- | --- |
  | `live · updated 1s ago` | ◉ | ok | 画面を取れている |
  | `idle · checking every 5s` | ◦ | dim | 動きがなく、間隔を空けて見ている |
  | `stale · last screen 14s ago · retrying` | ✗ | err | 取れていない |
  | `sending` | ◌ | dim | 送っている |
  | `queued · agent is busy` | ◉ | secondary | 送ったがまだ入力されていない(TUI の「未送信 ◉ secondary」と同じ) |
  | `delivered 12:37` | ✓ | dim | 入力された(TUI の「送信済み ✓ dim」と同じ) |
  | `not sent · retry` | ✗ | err | 送れなかった |

  鮮度と送達は画面に出す。`queued` は pekoed が知れるかを確かめ、無理なら最初は出さない。ポーリングの間隔は今の固定のまま(決まったこと 8)
- **記号だけ色、語は text か dim。** 表のセル(Pipeline の `✓ done`)、ゲート(`✓ land pekoe land done`)、鮮度の行は、記号を状態色にして語を dim(または text)にする。語まで色にするのは「人の番」を目立たせたいときだけ(Pipeline の工程の箱の `◉ you` は warn、受信箱のカードの `✓ merge ready` は secondary。docs/ui-guidelines.md の「状態の表現」の「人の番」と ✓ の色の規則)
- **過ぎたものは行ごと dim。** マージ済みの Pipeline の行、閉じた依頼の行は記号も語も dim に落とし、残すのは状態を区別する記号 1 つまで(モックの `↣ Merged` の ↣ だけ secondary)
- **ゲージは数値とペア**(TUI と同じ)。値は ok、80% を超えたら warn(TUI のゲージの規則。モックはまだ ok だけ)、残りは border。`Context 14%` のように % を必ず添える
- **棒グラフ**: 過去の日は dim、今日だけ secondary(TUI のスパークラインの「最新点だけ secondary」と同じ)
- **状態語は英語**: 一覧と表では英小文字の短語(`run`・`idle`・`done · 7d`)、ラベルとして独立するところ(サイドバーの 2 行目、カードの見出し)は文頭大文字(`Ready to merge`・`Permission needed`)。モックの書き分けに合わせた

## フォーカス

GUI のフォーカスは 3 つの層に分け、それぞれ表し方を 1 つに決める。

| 層 | 何を示すか | 表し方 | どこ |
| --- | --- | --- | --- |
| **注意のフォーカス** | その画面で人が次に扱うもの(1 つ) | 枠を primary → primary_end のグラデーション(1px)、見出しは primary | Dashboard: 先頭の Inbox カード 1 枚。Session: 送信欄。待っている間は送信欄の代わりに出る許可・質問のカード(決まったこと 10) |
| **選択** | いまどれを開いているか | primary 単色の 2px の線 | 選択中のタブの上辺、開いている行の左辺(地は raised) |
| **キーボードのフォーカス** | Tab で移ったときの位置 | primary 単色の輪(`:focus-visible`、2px、少し離す) | 押せるものすべて。マウスで押したときは出さない |

- **グラデーションは 1 画面に 1 つ。** TUI の「フォーカスは常に 1 つ」を、GUI では「注意のフォーカスは 1 つ」と読む。Inbox に複数のカードがあっても枠がグラデーションになるのは先頭(人が今答えるもの)だけで、ほかは border の枠
- **「カードに primary の枠を使わない」(TUI)との関係**: TUI ではフォーカスがパネルの単位だったのでカードに使わなかった。GUI ではパネルの枠が無いので、注意のフォーカスをカードの枠に移した。カードに primary を使うのは「注意のフォーカス」のカードだけで、ほかのカード(許可・質問以外の通知など)は border の枠のまま
- **選択の線は単色。** タブと行はたくさん並ぶので、グラデーションにすると「注意のフォーカス」と見分けがつかなくなる
- **キーボードのフォーカスの輪はモックに無い。** この文書で足した(ブラウザの既定の輪は色が役割に合わないので、primary の単色に替える)。注意のフォーカスと重なったときは輪を優先して見せる
- hover は選択と見分けられるようにする(推奨: 地を 1 段だけ上げ、primary の線は付けない。モックに hover は無い)

## アイコン

- **置き場所はクロームだけ**(TUI の原則 4)。アイコンレール・検索欄・テーマ切り替え・リポジトリの見出し。本文・表・カードの中には置かない(状態は記号の文字で表す)
- **描き方**: 16×16 の viewBox の線画(線幅 1.5、角は丸)、表示は 14〜18px、色は `currentColor`(つまり文字色の役割)。モックの SVG をそのまま使う。Nerd Font は使わない(ブラウザに無い)
- **同じ概念には同じアイコン**(TUI と同じ)。GUI の語彙(モックから):

  | 概念 | 形 | 置き場所 |
  | --- | --- | --- |
  | Sessions | 重なった 3 枚の板 | レール |
  | Worktrees | ブランチ(3 つの丸と枝) | レール |
  | Changes | 書類に +/− | レール |
  | Settings | 歯車 | レール(下端) |
  | 検索 | 虫めがね | タイトルバー |
  | テーマ | 半分塗った丸 | タイトルバー |

  TUI の語彙(Sessions は nf-md-robot など)とは形が違う。GUI ではこの表を正とし、足すときはこの表に足してから使う
- **アイコン単独で意味を持たせない。** レールのボタンは `aria-label` と、hover で名前を出す(推奨)
- **SVG の組み方**: 静的な HTML(`gui/index.html`)に書くか、JS から `createElementNS` と数値の属性だけで組む(docs/gui.md の脅威モデルの XSS の行)。`style` 属性は使わない(下の「実装の制約」)

## 画面の構成

細かい寸法はモックを正とする。ここには構成の要点と、原則に関わる決めごとだけ。

### 共通の枠

上から **タイトルバー → 本体(左サイドバー+メイン) → ステータスライン**。タイトルバー・サイドバー・タブ列・ステータスラインの地は chrome、メインの地は bg。

- **タイトルバー**: 左に `pekoe`、中央に検索とコマンドの欄(キーは `:`。TUI のコマンド入力と同じ)、右に pekoed の状態(`◉ pekoed running`)・テーマ切り替え・`n New session`
- **左サイドバー**: 左端に 48px のアイコンレール。その右に `SESSIONS` と件数、フィルタのチップ(All / Needs you / Running)、tapi のカード(名前・`orchestrator`・状態と経過・直近の 1 行)、リポジトリごとのグループ(セッションが 2 つ以上なら展開して 2 行、main だけなら `OTHER REPOSITORIES` に 1 行ずつたたむ)、最下行に dim の集計(`✓ 7 to review`。TUI のフッター行と同じ)
- **メインのタブ**: `Dashboard`、`tapi`、開いたセッション。選択中は地が bg(メインとつながる)で、上辺に primary の 2px
- **ステータスライン**: 左に primary 塗りのモードのピル(`DASHBOARD` / `TAPI`。bg の文字、600、字間 0.04em)、select 塗りのセグメント、dim の情報(件数・更新時刻)。右にキーヒントを 6 個まで(`key action`、key は secondary の太字、action は dim の英小文字)。TUI のボトムバーと同じ規則: いま扱っているビューのキーだけ、グローバルキーは載せない、狭ければ後ろから落として `?` を残す
- **キーが効くのは入力欄にフォーカスが無いときだけ。** 入力中の文字はキーとして奪わない(TUI の「エージェントに入力中の `!` は奪わない」と同じ考え)。送信の `⌘↵` だけは入力中に効く

### Dashboard

メインを 2 列に分け、左が本体、右が tapi パネル(chrome の地)。本体は上から 4 区画で、見出しは「太字の名前+件数+罫線」(絵文字なし)。

1. **Inbox**: 人の対応待ち。先頭のカードが注意のフォーカス(グラデーションの枠)。見出し(primary、18px)・状態・出どころ、実行対象を bg に沈めた 1 行、レポートの要約とリンク、ゲート(1 件 1 行、「記号 名前 説明」)、ボタン(主ボタンは 1 つ)。事実が先・推奨を既定にしない・確認シートは今の受信箱の規則のまま(docs/web.md の「受信箱(Inbox)の扱い」)
2. **Overview**: タイル 3 枚(いまの状態の件数、マージ数と日別の棒、今日のトークン)。枠は border、地は塗らない
3. **Pipeline**: 依頼のツリーと工程の箱のレール(Request / Branch / impl / review / PR / CI / merge / Status)。下の「Pipeline」
4. **Requests**: 開いている依頼を先頭に、閉じたものを直近 5 件。右上に台帳へのリンク

#### Pipeline

左から右へ、Request の箱 → ツリーの線 → Branch の箱 → 5 工程の箱のレール → Status。表に `✓ done` と `○` を並べるだけでは流れに見えず、同じ依頼から出たブランチのまとまりも見えなかったので、ツリーと箱にした(2026-11-22 のハンドオフ)。

- **ツリーは「ワークツリーを作った依頼」で組む。** ブランチは自分を作った依頼(`origin`。`pekoe new --request`)の下にだけぶら下がり、あとから `pekoe ledger link` で入った依頼(`later`)は線ではなく Branch の箱の札で見せる。r2 が入ってもブランチは r1 のグループに居続け、行を組み直さない。作った依頼が無いブランチ(手で作った、依頼なしの `pekoe new`)は Request の箱もツリーの線も付けず、Request の列に dim の `no request` と書いて依頼のグループの後ろに並べる。自分のブランチを持たない依頼は Pipeline に出さない(札だけ。依頼そのものは Requests で見る)
- **行と列**: グループの中はブランチ 1 本に 1 行、高さ 60px 固定。列は Request 132px・線 28px・Branch 288px・工程が「線 12px + 箱 84px」× 5・残りが Status。見出しは dim の 12px、工程の見出しは箱の真上に中央ぞろえ。グループの並びは、動いている行があるものを先に、新しい依頼が上。グループの中は状態の順(waiting → running → done・failed → その他 → landed。`/api/overview` と同じ。同じ状態の中は `/api/overview` の順)
- **Request の箱**: 高さ 44px・surface・border・角丸 8px。依頼の ID(太字)と dim の 11px で `tapi · 4 branches`(依頼元とブランチの本数。1 本なら `1 branch`)。グループの 1 行目と中心をそろえる
- **ツリーの線**: 1.5px の dim。1 行目へは水平にまっすぐ、2 行目以降は Request と Branch の間の中ほど(左から 14px)の幹から角丸 12px で曲がって入る。**幹は依頼ごとに 1 本の要素で引き**(行ごとに継ぎ足すと角丸の分の隙間と行の境目の段差が出る)、各行が描くのは曲がり角だけ。幹は最後の枝の曲がり始めで終わる。CSP で `style` 属性を使えないので、位置は行の高さ 60px を前提に CSS で決めてある(`.pl-trunk`・`.pl-corner`・`.pl-flat`)
- **Branch の箱**: 高さ 44px・surface・border・角丸 8px。ブランチ名(あふれたら末尾を省略)と札(縮めない)。押すとセッションのタブを開く。札は高さ 20px・角丸 10px・11px で、いまそのブランチが取り組んでいる依頼(open のもの)は `◉ r2`(◉ と枠が ok、文字は text)、済んだ依頼は `+r2`(枠 border、文字 dim)
- **工程の箱**: 幅 84px・高さ 28px・surface・角丸 6px・12px、「記号 語」を中央に。済み `✓ done`(PR は `✓ #279`。✓ は secondary、枠は border)、進行中 `◉ now`(CI は `◉ 2/4` = 通った数/全体。◉ と枠が ok)、未着手 `○`(枠は border の破線)、失敗 `✗ fail`(✗ と枠が err)、人の番 `◉ you`(◉・語・枠が warn)。語は人の番だけ warn で、ほかは dim
- **箱をつなぐ線**: Branch の箱と impl の間、箱と箱の間を 12px で。緑にしない。到達した工程の手前(済み・進行中・失敗・人の番の箱の左)は dim の実線、まだの工程の手前は border の破線
- **Status**: 1 行目はセッションの状態(`◉ run · 2m`・`✓ done · 50s`。記号は状態色、語は text の英小文字)。2 行目は dim の 1 行で、あとから入った依頼で impl に戻った(`reopened by r2`。作った依頼が無いブランチでは `working on r2`)・失敗した工程とその理由(`CI: 1 failed`)・人のマージ待ち(`ready · your merge`)・マージを止めている理由(`merge waits on CI · agent running`)のどれか 1 つ。待ちは ✗ で並べない
- **過ぎた行**(landed): 記号・語・枠を dim / border に落とす
- **多いとき**: 8 行まで出し、残りは `Show N more`(押すと全部と `Show less`)

決めたこと(ハンドオフで未決だったもの。原則は docs/ui-guidelines.md の「状態の表現」):

1. **済んだ工程の ✓ の色は secondary。** 工程が「済んだ」は完了の色。ok の ✓ は合否の「合」(PR の CI 全成功・承認済みのハンク)だけに使う。CI の箱の done も secondary
2. **マージ待ち(人の番)は warn。** 確認待ちの ◉ warn に合わせる(語の `you` も warn)。エージェントが waiting のときの impl の箱も同じ `◉ you`。受信箱の `✓ merge ready` と TUI の `ready to merge` は「根拠が揃った」(完了)を言うので secondary のまま
3. **Status の 2 行目の文言**: `merge waits on <理由> · <理由>`。理由は merge.check の揃っていない条件を短い語にしたもの: `CI`(実行中)・`CI 1 failed`・`PR status`(まだ読んでいない)・`review`・`re-review`(PR の HEAD が変わった)・`merge state behind` など(CI が済んでいないときの UNSTABLE・BLOCKED は CI と同じことを言うので出さない)・`conflicts`・`earlier sessions`(after)・`agent running` / `agent waiting`(settled)・`pekoe land`。詳しい理由は工程の箱の title(ホバー)と受信箱のゲートで読む
4. **CI の全体の数**は PR のチェックの `pass + fail + pending`(pekoed が GitHub から読んだもの)。まだ読んでいなければ `now`
5. **失敗の行**: 失敗した箱だけ err。右の線と箱は未着手と同じ(破線・○)
6. **進行中の語は `now` のまま。** 状態語の `run` はセッションの状態(Status)の語で、工程の箱は「いまここ」を言う別の語にしておく(同じ行に `◉ run` と `◉ run` が並ぶと、どちらの話か分からない)
7. **狭い幅**: Branch の箱を 160px まで縮め、それでも入らなければ区画の中で横にスクロールする(最小 950px)
8. **札が多いとき**: 2 つまでは全部、3 つ以上は先頭の 1 つ(取り組んでいる依頼、無ければいちばん新しい依頼)と `+K`(残りの数)

### Session

タブの下にセッションのヘッダ、その下を 2 列(左が画面と入力、右が情報のパネル)。考え方は **「ターミナルをそのまま映さず、3 層に分ける」**:

1. **画面(読むだけ)**: `Screen` の枠に、エージェントの画面の末尾を素のテキストで出す(TUI の原則 4: 内容は素のまま、色はエージェントの色)。行が少ないときは下に寄せる。書体は等幅(決まったこと 1)。`Load earlier` は出さず 80 行のまま(決まったこと 7)。段階 2 の一部で、同じ枠の見出しの `Chat | Screen` で、Claude Code の会話を吹き出しで読む Chat に切り替えられるようにした(既定は Screen。下の「実装で決めたこと」)
2. **データ(枠に出す)**: pekoed が構造化して持っているものは、ターミナルの最下行から読ませず枠に出す。ヘッダに名前・役割・状態と経過・モデル・モード(`auto mode on` は warn)・鮮度、右パネルに `USAGE`(ゲージと %)・`BACKGROUND`・`LINKED`・`NOTICES`。**新しいデータには新しい API が要るものがある**(モデル・使用量・バックグラウンドのシェルは今の `/api/*` に無い。推測: 段階 2 以降。実装の PR で、今の WebSession(docs/web.md)にあるものから出す)
3. **入力(生キーではなく意図)**: 下端に固定。送達の表示、送信欄(注意のフォーカス)、質問待ちの間だけ今のキーパッド(質問カード)。モックの固定のキー列は出さない(決まったこと 5)。送信欄には `! Shell` を出し、`!` で始まる文は送る前に確認シートを挟む。`/ Commands`・`@ Files` は段階 2 の一部で足した(決まったこと 6。一覧から送信欄に文字を入れるだけで、送らない)

### Session states

エージェントが待っているとき、送信欄の代わりにカードを出す。

- **Permission needed**: `◉`(warn)・ツール名と待ち時間、コマンドを bg に沈めた 1 行、`Allow once`(主ボタン)・`Always allow`・`Deny`(キーは err)。どれも今の確認シートを通す(docs/gui.md の「決まったこと」5)。判断は画面で行う(docs/web.md の「allow / deny の扱い」)ので、カードの上の Screen は見えたままにする
- **Question from the agent**: 質問文、選択肢を 1 件 1 行のボタン(番号と説明)、最後に `Type something else`。今のキーパッド(`POST …/keys`、質問待ちの間だけ)で答える
- 中身(コマンド・質問文)はモックでは見本

## 実装の制約との整合

今の守り(docs/gui.md の「待ち受けの確認」・脅威モデル、docs/web.md)をそのまま守る。デザインのためにこれを緩めない。

- **CSP**(`webCSP`: `default-src 'self'; style-src 'self'; script-src 'self'; img-src 'self' data:; connect-src 'self'` …): 外のスタイルシート・フォント・画像を読まない。`style-src 'self'` は **`style` 属性(inline style)も断る**ので、モックの inline style はすべて `gui/gui.css` のクラスに移す。今のテスト `TestGUIStylesOnlyInCSS`(`internal/daemon/gui_test.go`)も HTML の `style` 属性と JS からの `style` の書き込みを禁じている。例外は今と同じく画面の色(`lib/term.js` が確かめた `#rrggbb` を CSSOM で当てる)と、ゲージの幅のような数値(推奨: CSSOM の `style.setProperty('--pct', …)` を数値だけ確かめて当てる。今のテストはこれも断るので、実装の PR でテストの例外をどう書くか決める。または `<meter>` / `<progress>` を使う)
- **フォント**: 同梱するなら `webui/` の下に置けば `default-src 'self'` で読める(`font-src` を足す必要はない)。まず同梱せず system-ui で組むので、フォントのファイルは無い。外からは読まない(決まったこと 2)
- **外部ライブラリなし**: CSS フレームワーク・アイコンのフォント・グラフのライブラリを入れない。グラフ(マージ数の棒・ゲージ)は CSS の箱か、SVG を `createElementNS` と数値の属性で組む(docs/gui.md の脅威モデル)
- **`textContent` だけで描く**: エージェント由来の文字(画面・報告の要約・吹き出し・質問文)は `textContent` で入れ、HTML を作る入口(`innerHTML` など)を使わない(`TestWebInboxScriptIsText` が `webui/` の下のすべての JS を縛る)。モックの `<a href>` の「Read report」は、今の受信箱と同じく `http` / `https` だけをリンクにする
- **テーマの切り替え**: `<html>` の属性(`data-theme`)を JS で変え、色は CSS の変数の切り替えで変える。`style` を書かない。選択は `sessionStorage` に置く(トークンではないが、`localStorage` はオリジンが毎回変わるので効かない。決まったこと 11)。タイトルバーのボタンは `System`(OS の外観に従う。`data-theme` なし)→ `Dark` → `Light` → `System` の 3 つを巡り、ボタンの語は今の選択。`System` に戻すと `sessionStorage` の選択も消し、OS の外観にまた追従する(`gui/theme.js`)
- **ポーリングは同じオリジンの `/api/*` だけ**(`connect-src 'self'`)。WebSocket やサーバーからの push は今は無い

## 決まったこと

原則の文書の PR(#253)で挙げた未決事項 12 件に、ユーザーが答えた(2026-11-21)。本文で「決まったこと N」と書くのはこの番号(docs/gui.md の「決まったこと」は「docs/gui.md の決定 N」と書いて区別する)。推奨と違う答えになったものは、そう書いた。

1. **Screen(エージェントの画面)は等幅に戻す**(推奨どおり)。Screen と、bg に沈めた実行対象の行(コマンド・パス・SHA)を等幅(今の `app.css` の `--mono`: `ui-monospace, "SF Mono", Menlo, monospace`)にし、ほかはプロポーショナルのまま。行の高さはモックの 1.7 から、枠線がつながる 1.35〜1.4(今の `#d-screen`。`app.css` が `11px/1.35`、`gui.css` が `line-height: 1.35`)に戻す。理由: Claude Code の画面には桁をそろえた表・box-drawing の枠・インデントで揃えた diff があり、プロポーショナルでは崩れる(モックの Screen には揃えた出力が無く、崩れるかは確かめられていなかった)。TUI の原則 4「内容は素のまま」は、内容をエージェントが描いたとおりに見せることでもある。コマンドの行を等幅にするのは、許可の判断で `--` や空白の数を読み違えないため
2. **書体はまず system-ui で組む(同梱しない)。** 指定は `system-ui, -apple-system, "Hiragino Sans", "Noto Sans CJK JP", "Noto Sans JP", sans-serif`(Mac ではラテン文字が SF Pro、日本語がヒラギノ。どれも端末に入っている書体を名前で指すだけで、何も読み込まない)。組んで見て許容できなければ、**代案として Inter の同梱を検討する**。推奨(Inter だけ同梱)から変わった。理由: system-ui はバイナリが増えず(0 バイト)、ライセンス文も要らず、リポジトリに MIT でないものが増えない。SF Pro も tabular figures を持つので、原則の「数字は tabular figures」はそのまま守れる。見た目がモックの Inter から少し離れるのは、組んだ画面で確かめてから判断する。代案の Inter の同梱の材料(残しておく): ラテン文字だけなら woff2 で数百 KB(推測: 400・500・600・700 の 4 つで 300〜450KB。測ってから決める)、`webui/` の下に置けば CSP の `'self'` のまま読める、ライセンスは SIL OFL 1.1(要確認: 版と Reserved Font Name の有無)でライセンス文を添える(ロゴと同じく README に MIT の対象外と書く)。Noto Sans JP は 1 つの太さでも数 MB あり(推測)、代案でも同梱しない。どちらでも Google Fonts には戻さない
3. **サイドバーにも「記号・色・語」をそろえる**(推奨どおり。たたんだ行の `OTHER REPOSITORIES` も同じ)。理由: (a) API がすでに TUI と同じ記号・色の役割・語を `look` / `pr_look`(`{icon, role, word}`、docs/web.md の WebSession)で返しているので、サイドバーだけ記号を落とすと実装の方が特別扱いになる。(b) モックのサイドバー自体が `◉ Running`・`✗ failed` と `Ready to merge`・`done · 7d` で混ざっていた。(c) 色覚の違いへの保険(TUI の理由と同じ)。(d) 記号に色を持たせれば語を text にでき、決まったこと 12 の「raised の上の文字」と両立する
4. **数字キーでのパネル移動は残さない**(推奨どおり)。数字は質問カードの選択肢(`1`〜`9`)に使う。理由: GUI には番号を出したパネルが無く(上の「GUI で変えるもの」の 7)、数字に意味が無い。TUI で質問に答えるときの手の動きと合う。ブラウザでは `⌘1`〜`⌘9` がタブの切り替えに取られている。ビューの移動はクリックと `:` のコマンド欄(検索)で足りる(推測: キーで移りたい人は TUI を使う)
5. **Session の固定のキー列は出さない。** 質問待ちの間だけ、今のキーパッド(質問カード)を出す。`esc interrupt`(エージェントを止める)は、段階 2 で生のキーではなく名前付きの操作(新しい API、確認つき)として検討する(推奨どおり)。**段階 2 の一部で実装した**: `session.interrupt` / `tapi.interrupt`(Escape を 1 回、エージェントが動いている間だけ。docs/gui.md の「段階 2 の一部」)。理由: docs/gui.md の決定 7(エージェントの画面への生の入力は GUI で作らない)と、今のキーパッドの守り(docs/web.md の脅威モデルの「キーパッドで許可メニューを操作する」: 質問待ちの間だけ、矢印・Tab・Space・数字・Enter・Esc だけ、`C-c` などの修飾キーは送らない)。モックのキー列の多くはその外にある。特に `⇧tab mode` は Claude Code の権限のモードを切り替える(auto mode に入れられる。モックのヘッダの `auto mode on`)キーで、`always` より広く許可を外せる(推測を含む: どのモードまで巡るかは Claude Code の設定次第。今のキーパッドも `BTab` を送れるが、質問待ちの間のメニューの中だけ)。`^c cancel` は修飾キーで、今の許可リストが意図して外している。`↑ history`・`↓ shells`・`^o verbose` はターミナルの画面を操作するキーで、読むだけの Screen と組み合わせると「ターミナルの再現」(決定 7 が作らないとしたもの)になる。`↵ enter`・`1–9 choose` は質問カードで足りる
6. **送信欄に `! Shell` のボタンを出す。`!` で始まる文は、送る前に確認シートを挟む**(シェルのコマンドとしてその場で実行されること・宛先・文の全体を見せる)。`/ Commands`・`@ Files` は段階 2 以降(コマンドとファイルの一覧を出す新しい API が要る。**段階 2 の一部で実装した**: `session.commands`・`session.files`、docs/gui.md の「段階 2 の一部: セッションの吹き出しと送信欄の / @」)。**推奨(`!` は出さない)から変わった。** 理由: 人は Claude Code のシェルモード(入力欄の先頭の `!` で、残りを許可ダイアログなしにコマンドとして動かす)を send でも使っていて、TUI でエージェントの入力欄に打つのと同じ操作として残す。run 窓(docs/gui.md の決定 7 が GUI で作らないとしたもの)は人がコマンドと対話する端末の再現で、こちらはエージェントの入力欄に 1 行の文を送るだけなので、send の範囲に入る。ただしシェルのコマンドの実行は取り返しがつかず、XSS や押し間違いで起きると被害が大きいので、普通の send(シートなし)と違い、必ずシートで「何がどこで実行されるか」を見せる。シートを出す判定は pekoed と同じにする(先頭の空白を除いて `!` で始まる文。PR #254 の `shellBang`)。脅威モデルの扱い: 原則の文書の PR で指摘した「send が先頭の `!` を断っていない」は、**人の send では `!` を通し、エージェント(token なし)の send と `session.new` の `prompt` だけ先頭の `!` を断る**方針になった。その修正は PR #254(`fix(daemon): token なしの send と new の先頭の ! を断る`)でマージ済み(docs/api.md の「人間だけの操作」の `session.send`・`session.new`、docs/web.md の脅威モデルの「エージェントが pekoe の API(unix ソケット)で許可待ちに答える」の行)。GUI・Web UI・TUI・CLI からの人の send は今までどおり通る
7. **`Load earlier` は Screen には出さない(80 行のまま)。** tapi の吹き出しは、今の transcript の `earlier` で前を読めるようにする。セッションの吹き出し(transcript)は段階 2 以降(推奨どおり)。**段階 2 の一部で実装した**: セッションの Chat(`session.transcript`)と、tapi とセッションの吹き出しの前のページ(transcript の `before` で `Load earlier`。docs/gui.md)。Screen は今も 80 行のまま。理由: Screen の `GET …/screen` は最後 80 行だけで、前を読むには tmux の scrollback を範囲で読む新しい API が要り、差分で取れるかも確かめていない。長い経緯を読むなら TUI か、transcript から作る吹き出しの方が向く。tapi の transcript は `GET /api/tapi/transcript` の `earlier` ですでに前のページがある(docs/web.md の API の表)ので、新しい API なしで作れる
8. **鮮度と送達の表示は入れる。ポーリングの間隔は今の固定のまま**(一覧 3 秒・画面 2.5 秒・吹き出し 2 秒、タブが裏なら止める。`gui.js` の `schedule`)。`queued · agent is busy` は pekoed が「入力欄に入ったか」を知れるかを確かめ、無理なら最初は出さない。状態に応じて間隔を変える(run と入力直後は短く、idle は長く)のは、`idle · checking every 5s` の表示を出すなら一緒に入れる(推奨どおり)。理由: 鮮度(最後に画面を取れた時刻、取れなければ stale)はページが自分で知っていて新しい API が要らない。送達は send の応答と、tapi では transcript の送信済みの印(`lib/chat.js` の ✓ / ●)で出せる。今は send の応答が返った時点しか分からない(推測)ので、queued と delivered の見分けは要確認。ローカル GUI は localhost なので今の間隔でも重さは小さい(ハンドオフの「Tailscale 越し」は前提違い。上の「仮のもの」)
9. **iPhone の Web UI の bubble_me も `#1c2c51` に変える**(推奨どおり)。理由: bubble_me は `/theme.css` の 1 つの変数(`--bubble-me`)で、iPhone の Web UI と GUI が同じ `theme.BubbleMe` から受け取っている(`internal/daemon/web.go`)。GUI だけ変えると、同じ役割の色が面によって違い、トークンを 2 つに割ることになる。`#003643` が深緑に見える不評は iPhone でも同じ。対 text 10.5:1 で下限も満たす。ui-guidelines.md のトークン表の bubble_me の行と注記は、実装の PR で直す
10. **送信欄の代わりに出る許可・質問のカードは、グラデーションの枠を引き継ぐ**(推奨どおり)。理由: 待っている間は、そのカードが「人が次に扱うもの」(注意のフォーカス)で、送信欄は出ていないので、1 画面にグラデーションは 1 つのまま。モックの Session states のカードが border の枠なのは、1 枚の見本の板に並べたためと読める(推測)
11. **ライトは `/theme.css` がダークと一緒に出し、既定は OS の外観に従う**(推奨どおり)。`/theme.css` はダークを `:root` に、ライトを `@media (prefers-color-scheme: light)` と `[data-theme="light"]` に出す(手でダークを選んだときのために `[data-theme="dark"]` も)。手で切り替えた選択は `sessionStorage` に置き、そのタブの間だけ覚える。ライトの色は既定の値で固定し、`[theme.colors]` の上書きはダークにだけ効かせる。`[gui] theme` の設定は入れない(要望が出てから)。理由: ローカル GUI のオリジンは `http://127.0.0.1:<port>` で、既定の `port = 0` では待ち受けを始めるたびにポートが変わる(docs/gui.md の決定 9)ので、`localStorage` に覚えても次に開いたときには別のオリジンで読めない。`[theme.colors]` はユーザーが自分のダークの端末に合わせて rice するためのもので、ライトの上書きの場(例: `[theme.light]`)は要望が出てから足す
12. **raised(開いている行)の上では dim とアクセントを文字に使わない。** 語は text にし、色は記号だけに持たせる(推奨どおり)。理由: 上の「コントラスト」のとおり、ダークの dim は raised の上で 3.9:1、ライトのアクセントは 4.2〜4.4:1 で下限を割る。記号は 3:1 で足りる部品として扱える。raised を明るく(ライト)・暗く(ダーク)して下限に入れると、chrome との段差がほぼ消え、開いている行が見分けられなくなる(計算: ライトの raised を L0.94 にするとアクセントは 4.57:1 だが、対 chrome は 1.02:1)。決まったこと 3 で記号を入れるので、この規則で行の情報は減らない

## 実装で決めたこと

見た目の PR で、文書に書いていなかったことを決めたもの、文書どおりにできずに変えたもの。

- **ライトは GUI のページだけ。** `/theme.css` のライトの節は `:root[data-gui]` に限った(`gui/index.html` の `<html data-gui>`)。iPhone の Web UI も同じ `/theme.css` を読むが、TUI と同じくダークだけのまま(Web UI まで OS の外観で変わると、今の見た目が変わるため)。bubble_me の変更(決まったこと 9)は両方に効く
- **chrome と raised の導出**: 既定のダークは表の hex(`#1a1927`・`#2a2939`)。`[theme.colors]` の bg を上書きしたときだけ、その bg の色相と彩度のまま L を +0.022 / +0.090 した色にする(`theme.WebPalette`)
- **GUI のページは `app.css` を読まない。** 共有するのは `/theme.css` と `lib/` のモジュールだけで、`lib/` が組む部品(吹き出し・画面の色・画像のサムネイル・確認シート)の見た目も `gui/gui.css` に書いた
- **タイトルバーの検索欄**は、サイドバーに出しているビューの絞り込み(Sessions なら名前・ブランチ・リポジトリ)。絞り込みの無いビューの間は無効で `Nothing to filter in <ビュー>`。モックの「コマンド欄」(`run a command`)は作らず、入口は「欄はビューのもの」まで(理由は docs/gui.md の「サイドバーのビュー」)。コマンドの実行・PR や依頼の検索は段階 2 の候補。`n New session` は段階 2 の一部で足した(docs/gui.md)
- **アイコンレール**は 4 つ(Sessions / Worktrees / Changes、下端に Settings。SVG はモックのまま)。選んでいるボタンは raised の地と text の文字、ほかは dim。4 つとも中身がある(空のビューは最後の Settings で無くなった)。Worktrees は Sessions と同じ部品(`side-head`・`sgroup-head`・`srow`)で、リポジトリの見出しの下に worktree の行を並べる。セッションの無い行はボタンにせず、hover でも地を変えない(押せない行を押せそうに見せない)。`main`・`detached`・`outside ~/worktrees` の印は 11px の dim(開いている行では text。決まったこと 12)、ポートは右端の dim(`sr-age` と同じ置き方)。差し込みの形は docs/gui.md の「サイドバーのビュー」。狭い幅ではレールをサイドバーの上端の横 1 列にする(Settings は右端)
- **Settings のビュー**(レールの下端。docs/gui.md の「Settings(読むだけ)」): 押せるものは無く(読むだけ)、行は button でなく div。節の見出しは config.toml の書き方のまま(`[web]`・`[agents.claude]`。大文字にしない: エージェントの名前は大文字小文字を区別する)の等幅 600 で、右に `N set`(dim)。キーは左に 1px の border の罫線を引いた字下げで、名前(等幅・text)・値(等幅。config.toml にあれば text、既定なら dim)・説明(11px・dim)の 3 行。名前の右に印: `set` は border の枠の小さなタグ(text。色の意味を持たせない)、`restart` は dim の語だけ、再起動待ちは `!`(warn は記号だけ)+ `waits for restart`(dim)。上の注意(再起動待ち・`config check` の警告・読めない)は記号だけ色で語は text。等幅にしたのは決まったこと 1 の「実行対象の行」と同じ理由(キーと値はコマンドやパスを含み、config.toml にそのまま書く文字)。ページの中の設定(テーマなど)はここに置かず、末尾の `THIS TAB` に一文だけ
- **Inbox のカード**: 見出しは pekoed の項目なら問いの文、エージェントの項目なら pekoe の言葉(`A decision asked by <slug>`)にし、エージェントの文は事実の後に「The agent says」として出す(事実が先)。主ボタンは `Answer…`(選んだら `<選択肢>…`)で、確認シートを通す。選択肢は既定で選ばない。PR の URL があれば `Open PR #n`。レポートの要約(エージェントの言葉)と `View diff` は今の API に無いので出していない
- **Overview** はタイル 3 枚: `Right now`(件数)、`Merged`(今日・7 日の数と日別の棒)、`Tokens today`(out / in / cache write / cache read)。後の 2 枚は `GET /api/stats`(GUI だけの API、docs/gui.md)の実データ。棒は SVG を `createElementNS` と数値の属性(`height` など)で組み、`style` は使わない。高さは 7 日のうち一番多い日を 28px にした比例(マージのある日は 4px 以上)、0 の日は border の 2px の台にして日があることを見せる。色は「棒グラフ」の規則どおり過去の日が dim・今日が secondary。数は各棒の `<title>`(`Wed 2026-11-18 · 4 merged`)と図の `aria-label` で読めるようにした。トークンの値は `pekoe stats` と同じ短縮(`state.ShortTokens`。丸めまでテストで突き合わせる)で、正確な数は `title`。stats が読めないときは数を出さず `✗ stats unavailable · <理由>`
- **Requests** は台帳(`GET /api/ledger`)から作る。開いている依頼(◉ ok、`open → <セッション>`、経過)を先頭に、閉じたものを閉じた順に直近 5 件(行ごと dim、記号は ✓ だけ、語は `done`・`dropped`・`chat`、pekoed が自動で閉じたものは TUI と同じ `closed by pekoe`)。依頼の id は TUI と同じ `r123`。**`Open ledger` は別の画面ではなく、その場の展開にした。** 理由: レールの別ビュー(台帳の画面)は今の範囲の外で(上の「アイコンレール」)、展開なら同じ行の形のまま、Dashboard の文脈(開いている依頼とその工程)から離れずに閉じたものを遡れる。見出しの右端の button(`aria-expanded`)で、開くと閉じたものを 500 件まで出し、それより古いものは `+N older · pekoe ledger --all`。長い文は 1 行で切り、`title` で全文
- **tapi パネル**は tapi の transcript の吹き出し。モックの「送受信の一覧(差出人 → 宛先・種別)」は API に無い。`T Reset` は段階 2 の一部で足した(docs/gui.md)。前を読むのは、ページが持っている分(最大 3000 件)を `Show earlier` で 120 件ずつ出し、出し切ったら `Load earlier` で transcript の前のページを読む(`before`。段階 2 の一部で足した。前は「ここには無い、TUI で」と出していた)。先頭まで読めば `start of the conversation` の区切り(決まったこと 7)
- **Session の Chat と Screen**: 画面の枠の見出しの左に `Chat | Screen` の切り替え(枠線の中に 2 つのボタン。押されている方はサイドバーのチップと同じ raised の地と text の文字で、ネオンは使わない)。既定は Screen(Session の 3 層の「画面(読むだけ)」が主で、許可と質問は画面で判断するため。Chat には tool_result が無い)。選んだものはそのタブの間だけ覚える。Chat を選んでいても、許可待ち・質問待ちの間と、読めない間は Screen を出し、見出しの右に `! ` と理由(send-note と同じ形、warn は記号だけ)。Chat の見出しは `from the transcript · no tool output` で、Screen の `Pause` は隠す。吹き出しの見た目は tapi のパネルと同じ部品(`chatpane.js`・`lib/chat.js`)で、地は Screen と同じ bg
- **送信欄の `/ Commands`・`@ Files`**: `! Shell` の右に 2 つのボタン(`key action` の形。キーの文字 `/`・`@` は secondary)。一覧は送信欄の枠の中、文字の上に流れで出す(`dock` が縦にスクロールするので、浮かせると切れる)。地は bg、選んでいる行は raised で、その行の説明と出どころは text にする(決まったこと 12)。名前は等幅(コマンド・パスは実行対象の行と同じ扱い)、説明とディレクトリは dim で 1 行に切る。見出しに `↑↓ move · ↵ insert · esc close`。グラデーションの枠は送信欄のまま 1 つ(一覧に枠のグラデーションは使わない)。tapi には出さない
- **New session の issue**: フォームのリポジトリの下に `issue` の行(選んだ issue の `#N 題` か dim の `none`、`Clear`・`Pick issue…`)。一覧はその下にその場で開く(別のシートにしない。フォームの文脈のまま選べるように)。地は bg、行は 2 段(`#N 題` は text、ラベルとセッションは dim)で 1 行に切り、hover と選んでいる行は raised で、その上では 2 段目も text にする(raised の上に dim を置かない)。絞り込みは Chat | Screen と同じ `seg-toggle`(`assigned to me | all open`)。issue の文は確認シートのプロンプトの全文(等幅の `input whole`)で読む。主ボタンはフォームの `Continue` のまま 1 つ
- **tapi パネルの `t Start`**: tapi が動いていないときだけ、ヘッダの `T Reset` の左に出す(終了していれば `t Restart`)。破壊的でないので主ボタンにも err にもしない(キー文字は secondary、Reset のキー文字だけ err)
- **Changes のビュー**(レール。中身と API は docs/gui.md の「Changes のビュー」): 行は Sessions と同じ `srow` の形で、1 行目が状態の記号(`A` ok・`M` warn・`D` err、11px・700・等幅で桁をそろえる)・ファイル名・`+N −N`(tabular-nums)、2 行目がディレクトリ(dim)と `⚠ <slug>`。差分は同じサイドバーの中で bg の地の枠に出し、**等幅で折り返す**(コードは桁がそろわないと読めないので Screen と同じ扱いにした。サイドバーは 252px なので横には流さない)。色は `+` / `−` の記号と状態の記号・⚠ だけで、追加・削除の行に地の色は付けない(差分の本文はエージェントの文で、色で強調しない)。ハンクの見出しは dim、ハンクの間は border の罫線。主ボタンは無く、`← Files` は `btn sm`、右に dim の `read only`
- **Session の右パネル**は `/api/sessions` にあるもの(SESSION・CHANGES・LINKED・NOTICES)と、`AGENT` の節(モデル・effort・モード・Context のトークン数。`GET /api/sessions/{slug}/panel`、docs/gui.md の「段階 2 の一部: Session の右パネル」)。ヘッダではなく右パネルに置いた(ヘッダは名前・状態・鮮度で埋まっていて、エージェントの自己申告の値を状態と並べないため)。モードは語だけで、`auto mode on` と `bypass permissions` の語を warn(トークン表の用途「auto mode」。ネオンは 1 語で 1 行)、ほかは text。Context は数だけ(`115.4k tokens`)で、% とゲージは出さない(窓の大きさが無い。上の「ゲージは数値とペア」の % を偽らない)。`NOTICES` の `✓ Update installed · 旧 → 新 · restart the agent to apply` の記号は secondary(完了: 更新は入り済み)。読めないときは `✗ unavailable · 理由`、Claude Code でないエージェントは `◦`(dim)と理由の 1 行。USAGE(5h / 7d・Context の %)は statusline の中継の後、Cost・BACKGROUND は出さない
- **送達**: `delivered` は send の応答が返った(pekoed がエージェントの入力欄に打った)こと。エージェントが取り込んだかを pekoed は知らないので `queued · agent is busy` は出していない。送れなければ `✗ not sent · <理由>` と `Retry`
- **鮮度**: `◉ live · updated Ns ago`・`✗ stale · last screen Ns ago · retrying`・一時停止・選択中の保留。間隔は固定なので `idle · checking every …` は出さない(決まったこと 8)
- **キー**: 入力欄の外でだけ効く。`:` 絞り込み、許可のカードで `y` / `A` / `n`(確認シートを開くだけ)、質問のカードで `1`〜`9`、送信欄で `⌘↵`。ステータスラインにはそのビューのキーだけを出す
- **`!` の判定**は `gui/shell.js`(pekoed の `shellBang` と同じ。`TestGUIShellBangMatchesPekoed` が同じ入力で突き合わせる)
