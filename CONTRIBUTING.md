# Contributing

## Policy

pekoe is a personal project, and **pull requests are not accepted**. Bug reports and feature requests are welcome as [issues](https://github.com/sakamosu/pekoe/issues). Please report vulnerabilities privately instead, as described in [SECURITY.md](SECURITY.md).

The rest of this file describes how the project is developed and released, for reference. The design docs under `docs/` are in Japanese.

## Development

```sh
make build && make test     # go vet + go test (default and -tags web) + headless nvim tests
```

Inside an agent's sandbox (Claude Code's, which pekoe starts agents in), binding a unix socket or a TCP port is refused, so the integration tests that need a real socket, port, tmux server or nested sandbox (`sandbox-exec` / bwrap), and the headless nvim tests, are skipped there with the reason; `make test` then ends with a note saying so. Run `make test` outside the sandbox (in your own terminal) to cover them. The other tests run everywhere: they reach stand-in daemons and HTTP servers in memory (`internal/testenv`).

The Web UI (`internal/daemon/webts.go`) is only in `-tags web` builds. The default build must not pull in Tailscale: nothing but `webts.go` imports `tailscale.com`.

### Trying things in a sandbox

To test or try pekoe without touching your real environment, isolate it with `PEKOE_HOME` (settings and state), `PEKOE_SOCK`, `PEKOE_TMUX_SOCKET` and `PEKOE_WORKTREES`. `scripts/sandbox.sh` sets all four:

```sh
scripts/sandbox.sh                    # start an isolated daemon and drop into a subshell; cleaned up on exit
scripts/sandbox.sh pekoe new feat/x   # run a single command
WEB=1 scripts/sandbox.sh              # with the Web UI build
```

It creates the four in a temporary directory and starts a daemon with a `pekoe` built from the current source (`PEKOE_BIN` points it at a prebuilt binary instead). When it ends, including on failure or Ctrl-C, it stops the tmux server with `pekoe daemon stop --kill-agents --yes` and deletes the temporary directory.

If you set up an isolated environment by hand, clean it up at the end with `pekoe daemon stop --kill-agents --yes` under the same environment variables (`pekoe daemon stop` alone leaves the tmux server and the fake agents behind). The tmux server's pid is recorded at startup in `$PEKOE_HOME/share/tmux-<socket>.pid`, so it can be stopped even when `kill-server` can't reach it (for example with a different `TMUX_TMPDIR`).

- Never use `--kill-agents` with `PEKOE_TMUX_SOCKET` empty or set to `pekoe`: that stops every real agent
- Unix socket paths are limited to about 104 bytes on macOS, so put the isolated directory somewhere short, such as directly under `/tmp`

### Re-taking the README screenshot

`scripts/screenshot/run.sh` rebuilds `docs/images/screenshot.png` in a sandbox with a fictional repository and a fake agent (macOS and Google Chrome; `PEKOE_CHROME` overrides the Chrome path).

## Cutting a release

Pushing a `v*` tag makes GitHub Actions (`.github/workflows/release.yml`) do these in order; if any step fails, the release stays a draft and is not published:

1. Cross-build 4 platforms × default / `-tags web` with GoReleaser (`.goreleaser.yaml`), and sign and notarize the macOS binaries (see below)
2. Create the release **as a draft** with the archives, `checksums.txt` and a changelog since the previous tag (`release.draft: true`; GoReleaser uploads every asset to the draft)
3. Attach build provenance (an attestation, `actions/attest`) to each archive listed in `checksums.txt`
4. Publish the draft (`gh release edit <tag> --draft=false`, with `--latest` unless it is a prerelease such as `vX.Y.Z-rc.1`)

Publishing comes last because, with immutable releases on (below), assets can't be added to or replaced in a published release, and because `pekoe update` refuses a release from v0.4.0 on (`selfupdate.ProvenanceFrom`) that has no provenance: a published release should never be without one. To retry a failed run, re-run the workflow: `release.replace_existing_draft` deletes the draft of the same name and starts over. If you give up on a tag instead, delete its draft by hand (Releases → the draft → Delete).

- `THIRD_PARTY_LICENSES` in the archives is generated by GoReleaser's `before.hooks` with `scripts/third-party-licenses.sh`, once for the default build and once for `-tags web` (it concatenates the license texts of the modules found by `go list -deps` and of Go itself, and stops if a module has no license file). Its output directory `build/` is not committed
- Builds use only the Go in go.mod's `go` line (`GOTOOLCHAIN=local`). Before building, govulncheck runs with the same Go for the default and `-tags web` builds and stops the release if a known vulnerability is reachable
- `.github/workflows/govulncheck.yml` runs govulncheck for both builds on push, on pull requests and weekly. Locally: `make vulncheck`
- Workflow actions are pinned to commit SHAs and bumped by Dependabot (`.github/dependabot.yml`)
- The version is set from the tag through ldflags and shown by `pekoe version` (a local `make build` uses `git describe`; a plain `go build` gives `dev`)

```sh
git tag vX.Y.Z && git push origin vX.Y.Z
goreleaser check                        # validate .goreleaser.yaml
goreleaser release --snapshot --clean   # try it locally (output in dist/; nothing is published)
```

After the release is published, check it as a user would: `gh release view vX.Y.Z -R sakamosu/pekoe --json isDraft,isImmutable,assets` and `gh attestation verify <archive> -R sakamosu/pekoe --signer-workflow sakamosu/pekoe/.github/workflows/release.yml --source-ref refs/tags/vX.Y.Z`.

### Repository settings for releases (do these before cutting v0.4.0)

`release.yml` relies on two repository settings that only an admin can change. Set them up in this order, before pushing the v0.4.0 tag:

1. **The `release` Environment** (Settings → Environments → New environment → `release`). Add yourself as a required reviewer, and under Deployment branches and tags choose "Selected branches and tags" and add a tag rule `v*`. The `goreleaser` job waits for approval before it starts, and only a `v*` tag can use the environment. Do this first: if a tag push runs `release.yml` while the environment doesn't exist, GitHub creates it on the fly with no protection. The signing secrets go here too (see below)
2. **Immutable releases** (Settings → General → Releases → "Enable release immutability"; or `gh api -X PUT repos/sakamosu/pekoe/immutable-releases`). Once a release is published, its assets and its tag can't be changed or deleted, so nobody (an agent with a `repo`-scoped `gh` token, say) can swap an archive and `checksums.txt` of a published release. It applies only to releases published after it is turned on; v0.1.0 to v0.3.0 stay mutable. Check it with `gh api repos/sakamosu/pekoe/immutable-releases` (`"enabled": true`)

Turn immutable releases on before the first release made with the draft flow (v0.4.0), so that v0.4.0 is immutable from the moment it is published. The draft flow works with or without it (drafts are never immutable), so the order of the two settings doesn't matter for the workflow itself, only for protecting v0.4.0.

### Signing and notarizing the macOS binaries

GoReleaser's `notarize.macos` (`.goreleaser.yaml`) signs the darwin binaries of both builds (default and `-tags web`, arm64 and amd64) with a Developer ID Application certificate and submits them to Apple's notary service. It uses [quill](https://github.com/goreleaser/quill), so it runs on the ubuntu runner without a Mac. It runs right after the build and before archiving, so the archives, `checksums.txt` and the attestations all cover the signed binaries. It waits for Apple's verdict (up to 20 minutes per binary) and fails the release if a binary is rejected. A bare binary cannot have its notarization ticket stapled, so Gatekeeper checks it online the first time.

If `MACOS_SIGN_P12` is unset or empty (forks, a local `goreleaser release --snapshot --clean`), this step is skipped and the binaries keep the Go linker's ad-hoc signature, as before.

The secrets live in a GitHub Environment named `release`, which the `goreleaser` job in `release.yml` uses (see "Repository settings for releases" above). Set it up before adding the secrets:

1. Create the environment first (Settings → Environments → New environment → `release`). If a tag push runs `release.yml` before it exists, GitHub creates it on the fly with no protection rules, and the release is built unsigned (no secrets)
2. Add required reviewers, and limit its deployment tags to `v*`, so a tag push waits for approval before the job can read the secrets
3. Add the secrets below as environment secrets of `release`, not as repository secrets (repository secrets are readable by any workflow without approval)

Required reviewers on a private repository need GitHub Enterprise; on Free, Pro and Team they work only on public repositories. Environments themselves (and their secrets and tag rules) need Pro or above on a private repository. On a private repository (a private copy, say) without those plans, either make it public or accept that the tag rule is the only protection.

| Secret | What |
|---|---|
| `MACOS_SIGN_P12` | Developer ID Application certificate and its private key as a `.p12`, base64-encoded |
| `MACOS_SIGN_PASSWORD` | the password of that `.p12` |
| `MACOS_NOTARY_KEY` | App Store Connect API key (`AuthKey_<KEY_ID>.p8`), base64-encoded |
| `MACOS_NOTARY_KEY_ID` | that key's Key ID |
| `MACOS_NOTARY_ISSUER_ID` | the Issuer ID shown on the App Store Connect API keys page |

To make them:

1. Certificate: in the Apple Developer account, Certificates → + → Developer ID Application (create the CSR with Keychain Access → Certificate Assistant → Request a Certificate From a Certificate Authority). Install the downloaded `.cer`, then in Keychain Access → My Certificates, select "Developer ID Application: …" together with its private key and export it as `.p12` with a password. Then `base64 -i cert.p12 | pbcopy` and paste it into `MACOS_SIGN_P12`
2. API key: in App Store Connect → Users and Access → Integrations → App Store Connect API, create a Team key with the Developer role. Download the `.p8` (only once), then `base64 -i AuthKey_XXXXXXXXXX.p8 | pbcopy` into `MACOS_NOTARY_KEY`, and copy the Key ID and the Issuer ID into the other two
3. Delete the local `.p12` / `.p8` copies you don't need, or keep them somewhere safe

To check a release: `codesign -dv bin/pekoe` should show `Authority=Developer ID Application: …` and a `TeamIdentifier` (instead of `Signature=adhoc`).

### Installing goreleaser

goreleaser is installed from the Go module proxy, both in the workflow and locally (GitHub release asset downloads are sometimes unavailable). Match the version to `GORELEASER_VERSION` in the workflow:

```sh
GOTOOLCHAIN=auto go install github.com/goreleaser/goreleaser/v2@v2.20.0
```
